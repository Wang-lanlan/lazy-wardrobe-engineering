# 主长文写作方案：从 0 推演一个 AI 穿搭产品

> 本文是「主长文」的**写作方案（提纲 + 执行计划）**，不是全文。
> 全文目标（用户确认）：**展示一个 PM / 产品人怎么从 0 推演一个 AI 产品**。
> 性质判定：主长文是这件「作品」的**主体（必写）**；公开仓仓库只是它的**证据附件**。

---

## 0. 文档性质与与仓库的关系

- **仓库 = 证据，本文 = 叙事主体**。文中用相对链接指向 ADR / 代码 / README，形成「结论 ← 证据」闭环。
- 本文**不重抄** README 费用表或 ADR 原文，只讲「是怎么一步步走到那个结论的」——表里没有的故事才是文章价值。
- 落点（全文）：公开仓 `docs/主长文-从0推演AI产品.md`（本方案先放 `docs/主长文-方案.md`）。

## 1. 读者与前提假设

- **读者**：转型 / 初级 PM、想做 AI 产品的个人开发者、招聘面试官。
- **假设**：读者懂基本产品概念；**不一定懂云开发 / 生图模型** → 任何技术约束都必须翻译成「对产品意味着什么」。

## 2. 核心论点（Thesis）

> 一个能落地的 AI 产品，不是「选了最酷的模型」，而是「在真实约束下，把每一步不可为变成可为」的连续决策链。
> 约束（60s 时长、出图成本、平台静默截断）——不是障碍，是**产品形态的塑造者**。

## 3. 逐节方案

每节给：目标 / 内容要点 / 引证来源（公开仓真实路径）/ 篇幅占比。

### §0 起点：为什么是「懒懒衣橱」
- **目标**：交代动机与冷启动 anchor，确立「为一个人、一天、已有衣服收敛出可出门答案」的产品边界。
- **内容**：
  - 个人痛点（166cm/45kg/窄肩/黄皮/雷区）→ 直接编码成推荐权重，而不是泛泛「智能推荐」。
  - 「可见的 AI = 可被评判的 AI」这一定调从第一天就立下（见 §5）。
- **引证**：`DESIGN.md`（品牌与人格定调）、`CONTEXT.md`（个人画像 anchor）。
- **占比**：~8%

### §1 第一性原理：把问题拆到不能再拆
- **目标**：展示 PM 的拆题能力——不急着选技术，先定义「什么叫一个好答案」。
- **内容**：
  - 推荐系统本质 = 在「已有衣服 + 当天约束（天气/场景/心情）」里收敛出 3 个能直接出门的答案。
  - 为什么是「3 个」而不是 1 个或 10 个（给用户决策权，但不过载）。
- **引证**：`CONTEXT.md`（六条铁律、月度额度口径）、`DESIGN.md`。
- **占比**：~10%

### §2 技术约束如何倒逼产品形态（核心节）
- **目标**：全文最值钱的一节——讲清「平台限制怎么变成产品决策」，而非「我用了什么技术」。
- **内容**：
  - **云函数 60s 硬限 → 两趟渲染**：一趟塞不下「人物底图 + 上装 + 下装 + 配饰」，拆成 pass1（主体）+ pass2（配饰）是唯一解，不是炫技。`-504003` 超时即此约束的具象。
  - **出图成本 → 月度额度**：按张计费倒逼「额度按北京时间算月」「预算闸预估式放行」。
  - **平台静默截断 / 无法主动日推 → 产品边界**：端 limit 默认 20、无法日推，决定「推荐是拉不是推」。
- **引证**：`docs/tickets/0009-two-pass-rendering/`、`docs/specs/0004-two-pass-render-and-image-role-labels.md`、`docs/.scratch/two-pass-render/`、`docs/adr/0004-on-demand-look-image-with-quota.md`、`CONTEXT.md`（平台硬限制③.5）。
- **占比**：~22%（最大节）

### §3 模型选型的三次转向
- **目标**：展示「选型不是一锤定音」，并嵌入费用三轮校准这条主线。
- **内容**：
  - 试衣（aitryon）2026-09-10 退役 → 改走「参考图 + 生图」路线（`docs/tickets/0008-model-lifecycle-migration/`）。
  - 万相 / Qwen 取舍（`docs/adr/0003-pluggable-siliconflow-image-provider.md` 思路，可插拔 provider）。
  - **费用三轮校准 ¥0.20 → ¥0.24 → ¥0.48**：1 参考图误算 → 3 参考图 → 两趟各 3 图。这串数字本身就是「不拍脑袋」的证据。
- **引证**：`docs/tickets/0008-model-lifecycle-migration/`、`README.md` §费用、`docs/adr/0003-*`（若存在）。
- **占比**：~18%

### §4 最贵的一课：不编数据
- **目标**：讲一条 PM 纪律——没有调查的数字，再好看也不能写。
- **内容**：
  - 主动删掉「多数用户每月实际出图 2–4 张」这类无据断言（即使它让方案显得更丰满）。
  - 引申：案例库署名也守同一纪律——硬约束凑不齐就诚实降级，绝不硬凑（`docs/adr/0012-*` + `.scratch/optimization-roadmap/issues/08-dual-gate-season-fit.md`）。
- **引证**：`README.md`（推荐依据 bullet）、`docs/adr/0012-inspo-constraint-and-temperature-dual-gate.md`、`docs/.scratch/optimization-roadmap/issues/07-three-level-badge.md`、`05-provenance-real-blogger-mapping.md`。
- **占比**：~12%

### §5 把「可见的 AI = 可被评判的 AI」做成铁律
- **目标**：这是本产品的差异化方法论，值得独立成节。
- **内容**：
  - 凡「云端读了哪个值决定结果」，都把实际取用的值回传前端自证（build 版本号、缓存键即输入、promptUsed 取景句）。
  - provenance 双轨：`docs/adr/0008-dual-track-provenance-and-transfer-mapping.md` + `0009-garment-image-must-enter-generation.md`。
- **引证**：上述两份 ADR、`CONTEXT.md`（铁律①输入即键、⑥版本盐）。
- **占比**：~12%

### §6 工程现实的耳光
- **目标**：PM 也要懂交付摩擦——让文章有血有肉，不悬浮。
- **内容**：
  - 本机环境坑（Edit EBUSY 静默丢段、push 拉锯、tracking ref 丢失）→ 交付不是写完代码就结束。
  - 教训：可离线测的页面控制器、反向验证门（short-circuit 证明门在守东西）。
- **引证**：`dev/demo-gates/README.md`、`CONTEXT.md`（工具坑、工程环境）。
- **占比**：~10%

### §7 复盘：重来会改哪三步
- **目标**：展示元认知——能说出「当时如果…」。
- **内容**：
  - 例：早一点把「两趟」当结构性约束而非临时方案；费用口径从第一天就按两趟建模；案例库准入闸前置而非事后补救。
- **引证**：综合上述各节。
- **占比**：~8%

### §8 证据索引
- **目标**：把文中引用汇成可点击清单，让「作品」可被核验。
- **内容**：ADR / 代码 / README 的相对链接表。
- **占比**：~0%（附录）

## 4. 风格与红线

- **Why before What**；先高层概念，再具体例子锚定。
- 每节至少一个**具体锚点**（真实片段 / 数字 / 决策句），不空谈。
- **不重抄** README 费用表 / ADR 原文；只讲「怎么走到结论」，表与结论靠链接。
- 所有数字**可溯源**（费用→`README.md` §费用；额度→`docs/adr/0004` + 代码）。
- 口语化、克制 emoji、不注水；结构化但不堆砌。

## 5. 篇幅与交付

- **全文**：约 2000–3000 字中文（不含代码 / 链接）。
- **落点**：公开仓 `docs/主长文-从0推演AI产品.md`。
- **发布**：仓库内首发；可选搬运博客 / 公众号（搬运时保留证据链接或改为截图）。
- **配图建议**（可选）：
  1. 决策链时间线（起点→拆题→约束→选型→纪律→复盘）
  2. 「约束 → 形态」对照图（60s/成本/平台限 各对应一个产品决策）
  3. 两趟渲染流程图（pass1 主体 / pass2 配饰）
  - 形式：mermaid 内联（仓库可读）或截图。
