# ADR 0008：双轨溯源 + 迁移对照 + 分层案例库

- **日期**：2026-09-02
- **状态**：已接受
- **相关**：ADR 0004（按需生图与额度）、ADR 0007（统一大脑与韩系 grounding）

---

## 背景

一次针对「灵感从哪来、怎么变成推荐」的代码审计，查出五个此前未被记录的事实：

1. **案例库没有一条 URL**。grep `brain.json` 全文，`http` 零匹配。10 条案例的 `source` 全是纯中文文本，不可点击、不可验证。
2. **案例从不进入生图 prompt**。`lookPrompt.buildPrompt()` 的签名里没有 `cases`/`inspo` 参数。卡片上的「✨ 灵感来源」与「AI 上身图」是两条独立管道，仅并排出现，制造出假关联。
3. **`freshCases.js` 的 case 结构化是假的**：`items`/`logic`/`transferable` 三个字段都是 `content.slice(0, 200)` 的同一段原文截断。
4. **`inspo` 没有任何校验**。`freshCases.js` 注释里那句「禁止编造：不杜撰博主名」是写给 LLM 看的祈使句，云函数里不存在 `inspo ∈ usedCases.source` 的白名单校验。LLM 吐什么字符串就原样高亮到页面上。
5. **产品自己拆了卖点**：`promptBuilder` 硬规则第 6 条把第 2、3 套定义成「韩女搭配」（1 件衣橱锚点 + 其余自由组合含 wish），等于内置了两个小红书。

同时确认一条平台硬限制：**微信小程序无法每日主动推送**。长期订阅消息仅对政务民生、医疗、交通、金融、教育、设备等类目开放，穿搭类目申请必驳；一次性订阅是「授权一次发一条」，且须由用户点击行为触发。

使用者提出的核心诉求：**参考的那套韩女/明星搭配必须可溯源，确保不是 AI 自己编的。**

## 决策

### 1. 三套全做「她怎么穿 → 你怎么穿」对照，但三套的对照对象不同

| 套 | 约束 | 对照对象 |
|---|---|---|
| 第 1 套 | itemIds 全部来自衣橱，wish 为空 | **用户自己的惯性穿法**（从 `looks` 集合历史推断） |
| 第 2、3 套 | 至少 1 件衣橱锚点 | 案例库（personal 优先，public 补位） |

第 1 套不对照韩女——它的卖点恰恰是「你衣柜里就有答案」，拿韩女对照等于暗示还得抄她。它该回答的是「**今天为什么别按老样子穿**」。

### 2. 溯源双轨：灵感行 + 规则行，都用受控枚举 + 白名单强校验

- **灵感行**：`inspo` 从自由文本改为 `inspoId`（受控案例 id），案例补 `url` + `fetchedAt`，页面可点击跳转。
- **规则行**：新增 `ruleRef`（受控 chapter id，取自 `brain.json` 的 `rules.chapters`），可展开查看规则原文。
- **共同校验**：新增纯函数 `lib/provenance.js`，做「输出值 ∈ 本轮注入的受控集合」校验。任一不通过 → 强制降级为 `FALLBACK_INSPO`（'通用韩系原则，无特定参考'），并按现有 `.inspo.gen` 弱化样式渲染。
- 这是把「希望 LLM 诚实」变成「LLM 没法不诚实」的那一步，是本次改造中**唯一不可省**的部分。

> **⚠️ 2026-09-02 修订（微信外链限制）**：上面「页面可点击跳转」在小程序内**不成立**。
> 微信对 Instagram（境外域）、小红书 / 抖音（竞品域）一律拦截，点开只提示「请在浏览器打开」。
> 因此 `url` 的真实用途是**溯源验证 + 展示出处文本**，点击行为降级为「复制链接 / 展示博主名」，
> **不得**设计成"点了就该跳到原帖"——那是必然落空的承诺。
> 案例卡片的溯源展示以**博主名 + 平台 + 抓取日期**为准，链接只是可选的深度验证入口。

**分层的理由**：两者证明的是不同的事——
- 灵感行证明「这个出处真实存在（有据可查）」；
- 规则行证明「这套搭配确实遵循了你定的规则」，永不过期、零外部依赖。

灵感链接 404 之后，规则行仍在，卡片不会退化成一句孤零零的「相信我」。

### 3. 案例库分两层，个人库优先

`cases` 增加 `origin: 'personal' | 'public'` 字段，`pickCases` 排序时 personal 优先，命中不足时用 public 补位。改动与现有「精确匹配优先」排序逻辑同构。

**依赖顺序警告**：必须先定来源再补 URL。若先给大众案例补完链接再换个人库，那轮检索工作全部作废。

#### 来源三级分级（2026-09-02 使用者确认方向：韩女风格 → 韩国来源优先）

产品的 grounding 是「韩系」（见 ADR 0007：*韩味来自"抄了某个真实博主某一套"的具体性，而不是规则本身*），
所以 personal 库的收录偏好是**韩国风格来源**——这正是本 ADR 背景第 1 条要修的毛病
（原案例库全是国内媒体二手转述 + 零 URL，韩味在转述中被稀释）。

但**不锁死平台**：机制开放（使用者给博主名就能入库），硬约束落在内容上
——可验证 url + 真实博主名 + 过 provenance 白名单。

| 级别 | 来源 | 处理 | 说明 |
|---|---|---|---|
| **一级** | 韩国一手：Instagram 韩国真人博主、韩国本土时尚站（HYPEBAE / 10 Magazine / Spread / Naver 时尚） | 直接入库 | 韩味最正、原汁原味 |
| **二级** | 中文韩女搬运：小红书 / 抖音的韩女搬运号 | 入库，但须填 `viaOriginal`（标注原始博主） | 最易消费、可点击，本质是二手 |
| **三级** | 国内媒体改写稿、"某韩星同款"无博主名、营销号拼凑 | **拒收** | 正是背景第 1 条要消灭的「不可溯源」来源 |

微博权重偏低：时尚博主多为国内二传或明星通稿，韩女一手少；抖音 / 小红书更合适。

> **红线（沿用 ADR 0007）**：**禁止编造博主名、明星名或链接**。
> 三级来源一律不入库——宁可案例库空着，也不注水。

> **⚠️ 2026-09-02 偏差处理（@rloiy）**：使用者明确确认的 @rloiy 仅能检索到三级渠道（搜狐/网易转述稿，无一手原帖直链）。身份与风格真实，但不满足一级/二级入库门槛。处理：以 `tier=3 / provenance-limited` 标记入库（personal-cases.json 的 p-013/p-014），**不冒充一级**；schema-check 对 tier=3 仅告警不失败；provenance.js 透传 `tier` 供前端展示「转述来源」弱化徽标。待检索到一级/二级直链即升级、移除 tier=3 标记。此为唯一已知的 tier=3 例外，**不代表三级可随意入库**——其余三级稿（如未确认博主、营销号拼凑）仍按拒收处理。

**personal 案例 schema**：见 `references/personal-cases.template.json`（5 条空槽 + 逐字段说明）。

相比现有 public 案例新增 4 个字段：`origin` / `tier` / `viaOriginal` / `fetchedAt`。
关键改动是把 `blogger` / `platform` 从 `source` 文本里**拆出来独立存储**——
卡片展示用 `source`，溯源校验用 `id`，两者分离，避免旧实现「拿整段 source 文本去比对」的脆弱性
（那正是 LLM 吐 `'灵感来自 1017kk 白开水穿搭：…'` 这类加了前缀后缀的串就无法判定的原因）。

> ⚠️ `transferable` 必须与 `colorLogic` **内容真的不同**。旧实现的 `items`/`logic`/`transferable`
> 三个字段是同一段原文截断（背景第 3 条），等于没结构化。模板里已显式标注，入库时逐条检查。

### 4. 上身图改为 flat lay，只画用户自己的单品

- 人像全身图退役。理由：迁移要的是「她的逻辑 + 我的衣服」，而生图给的是「她的逻辑的一半 + 一个陌生女人 + 幻觉出来的衣服」，两头都不落地。
- 改为 flat lay 平铺图（不画人，规避肖像权）。
- 沿用 ADR 0004 的按需触发 + 组合缓存 + 月额度，不自动生成。
- **`PROMPT_VERSION` 必须 +1**（v3 → v4），否则旧缓存被继续命中。

> **⚠️ 2026-09-02 修订（见 ADR 0009）**：本条中「只画用户衣橱里的真实单品」这一约束
> **在当前架构下无法兑现**——单品实物图从不进入生成链路，文生图 / flat lay 画出的
> 仍是模型对文字描述的想象。真正能兑现它的只有把平拍图真实穿到人像上的专用模型（已终止），而该 provider
> 当前是空壳。在修复并验证之前，生成图一律视为**氛围示意图**，UI 必须标注。

### 5. 主动推送不做

小程序无每日推送能力，不做无谓投入。若日后需要「懒懒出现在你面前」，走云函数定时触发器预生成 + 打开即见（见 ADR 待补）。

### 6. 只把「加一个博主」固化成 skill

整条「检索 → 洗净 → 入库」不 skill 化——固化一个错的过程只会让错误跑得更快。真正值得固化的只有最后一段：使用者给博主/明星名 → 定向检索 → 抽取单品/配色逻辑/可迁移点（三个字段必须真的不一样）→ 写入 personal 库。它有明确输入、明确验收标准，且会被反复使用。

## 取舍

**放弃的**：
- 人像上身图的视觉冲击力
- 每日主动推送
- 大众案例库作为唯一来源的地位

**换来的**：
- 溯源物理上可验证，编造不再可能
- 卡片上的每张图、每行字都能落到「我的衣服」或「你的规则」
- 与小红书形成真正的差异：小红书给大众流行，这里给你关注的人的穿法，且落到你衣柜里

**新增的维护成本**：
- 案例链接会 404，需要 `fetchedAt` + 失效提示
- 个人库需要使用者定期补充博主

## 实施顺序（强依赖，不可颠倒）

1. 定案例来源（personal 博主名单）→ 2. 补 URL + `fetchedAt` + `origin` → 3. `brain.json` schema 升级
4. `lib/provenance.js` + 单测 → 5. `promptBuilder` 输出 `inspoId` + `ruleRef` → 6. `recommendCore` 接校验
7. 前端：灵感行可点击 + 规则行可展开 + 对照区 → 8. flat lay 生图（`PROMPT_VERSION` v4）
9. 惯性提取（第 1 套对照）

第 1 步必须先做，否则补 URL 的工作会作废。

> **2026-09-02 四次修复（真因：fresh 层把个人灵感库挤出案例池 + fresh 因类型不一致全是死数据）**：
> 三次修复后**仍**见三套全 fallback，`brain.cases` 从二次修复起**恒为 16，一次都没变过**。
> 前三次全部误判为「LLM 自报不可靠」，实际病根在案例池构成，与 LLM 无关：
> - **病根 A（主因）**：`aiRecommend/lib/freshCases.js` 的 `mergeFreshCases` 原实现
>   `freshCases.concat(base).slice(0, 16)` —— fresh 排最前，一刀切 16 条。
>   `refreshCases` 一次写 **12 条** fresh（`lib/freshCases.js` 封顶 12），
>   而 personal（14 条 / 六位 IG 博主）经 brainLoader 合并后排在 fresh **之后** →
>   24 条被砍成 16 条，**博主案例只剩前 4 条，10 条 public 全灭**。
>   `16` 是 `slice(0,16)` 的**确定性指纹**：只要 fresh 非空，输出恒为 16，与输入 22/24/36 无关。
>   这正是它骗过前三轮的原因——总数"看起来正常"，构成错了看不出来。
> - **病根 B（fresh 是死数据）**：`refreshCases` 写入的 fresh 案例 `season`/`scene` 是**数组**（`['秋冬']`/`['通用']`），
>   而 `pickCases` 原实现是字符串比较 `c.season === se` → 数组永远匹配不上 →
>   **12 条 fresh 一条都进不了 prompt，却稳稳占着 12 个名额**。典型的「类型不一致导致静默失效」。
> - **病根 C（元问题：无法验收）**：每一轮都以「⚠️ 必须重新部署」收尾，但没有任何手段验证"云端到底加载了什么"。
>   日志只有一个 `brain.cases` 总数，是个聚合值，构成错了照常显示得像正常。
>   这才是同一个 bug 能连修四轮的真正原因——**不是修错方向，是从来没法确认修没修好**。
>
> 修复（三处，均已补测试钉死）：
> - `mergeFreshCases`：**personal 名额独立、完全不参与封顶**，fresh 继续膨胀也挤不掉；

> - `pickCases` 增 `toList`/`fieldMatches`：字符串与数组一视同仁，fresh 不再因类型不匹配被静默丢弃；
>   同时保留过滤语义（季节不符的数组案例仍被挡，未放宽成全通过）。
> - 新增 `brainLoader.caseStats(brain)`：返回 `{total, personal, public, fresh, bloggers[{name,n}]}`，
>   随云函数响应 `caseStats` 回传，并渲染在推荐页底部（`case-stats` 脚注）。
