# ADR-0016 · 抠图整体改为腾讯云数据万象 GoodsMatting（退役客户端色键 + 百炼绿幕重绘）

- 状态：采纳（2026-09-10，用户拍板「用腾讯云数据万象 GoodsMatting 实现，省事又放心」+「全量走 GoodsMatting」）
- 关联：ADR-0015（被本 ADR 取代）、ADR-0011（start/poll 异步两段式）、docs/specs/0006-upload-item-page.md（决策 4 抠图）

## 背景

ADR-0015 定了「三级降级」：客户端色键 → 色键失败走百炼 `wanx2.1-imageedit` 绿幕重绘 → 再色键 → 全失败回退原图。
真机跑下来，用户反馈**抠图效果不佳**，根因是三层各自都有天花板：

1. **客户端色键（`matting.js`）的算法天花板**——单一边缘带中位数参考色 + Chebyshev 硬阈值（≤30/255）+ 无羽化、无连通域/形态学处理。背景有渐变、阴影、杂物时，参考色代表性崩塌；硬阈值导致边缘锯齿；参考色附近的衣物像素被一并抠掉（衣服上打洞）。这是纯算法层面的上限，调阈值救不了（ADR-0015 自己也这么写了）。
2. **百炼绿幕重绘是「生成式」而非「真抠图」**——`wanx2.1-imageedit` 重绘背景，模型没有 alpha 通道，只能把背景画成绿色再让色键去抠。**风险不对称且不可接受**：生成模型会顺手改动衣物本身（颜色轻微偏移、纹理/图案细节丢失、纽扣拉链变形）。衣橱是推荐系统的真源——一件「正红」被重绘成「偏橘红」，后续推荐的颜色逻辑就建立在假数据上，而且**全程静默**（用户看不出来，只觉得「怎么推荐得不对」）。这正撞在本项目最忌讳的「错位不可自证」元问题上。
3. **两段式链路慢且贵**：难图要走「提交 imageedit 异步任务 → 轮询 → 下载绿幕图 → 重跑色键」，链路长、每张 0.14 元，还可能失败在任一段。

结论：**抠图这件事不该由生成模型承担**。需要的是一个输出带 alpha 通道的**真抠图**服务。

## 决策

**抠图整体改为腾讯云数据万象（Cloud Infinite, CI）GoodsMatting，全量走它，色键与百炼链路整体退役。**

```
任意背景的衣物照 → mattingGoods 云函数 → 数据万象 GoodsMatting（真抠图，输出透明 PNG）
                                       → 回传微信云存储 → 识别/入库
```

要点：

- **detect-url 模式**：GoodsMatting 支持对任意公网可访问 URL 抠图，不必先把图搬进 COS。链路 = `getTempFileURL(fileID)` 拿微信云存储临时链接 → 把链接作为 `detect-url` 传给数据万象 → 拿回透明 PNG。**微信云存储仍是衣橱唯一真源**（ADR-0001），COS 桶可以始终是空的，只作为签名入口。
- **同步接口 + start/poll 外壳**：GoodsMatting 本身是同步 GET（`?ci-process=GoodsMatting&detect-url=...`，返回 `image/png`），实测数秒级。但客户端 `wx.cloud.callFunction` 有 3s 硬超时（ADR-0011），故仍套 recognizeItem 的 start/poll 外壳：`start` 写 task doc + fire-and-forget 启动后台抠图立即返回 taskId，`poll` 只读 db。
- **签名自实现**（`lib/cosSign.js`）：用 SecretId/SecretKey 按 COS 请求签名算法（sha1）自签，不引 SDK。纯函数 + 离线单测。
- **错误分类**（`lib/parse.js`）：把数据万象的 XML/JSON 错误体归成 `signature / arrears / notactivated / ratelimit / image / permission / unknown` 七类，每类给出不同的中文处置提示；`retryable`（欠费/未开通/签名/权限四类重试无意义）由云函数算出后回传前端——**不在前端复刻这份名单**（跨端复制正是本项目反复踩的静默错位源，铁律三/六）。
- **前置条件**（缺一必报错，错误 kind 见 parse.js）：① COS 桶已绑定数据万象；② 已开通数据万象「AI 内容识别」服务；③ 密钥具备 `cos:GetObject` + `ci:CreateGoodsMattingJob` 权限。

## 备选被拒

- **保留客户端色键作为「0 成本快速路径」，只对失败图走 GoodsMatting**：看似省钱，但色键的「成功」本身就不可信（打洞/锯齿/半透明，coverage 落在正常区间就出图了）——**留它 = 留住用户抱怨的那个质量**。用户明确拍板「全量走 GoodsMatting」，不做分层。省下的钱不抵「每条入库的图都要人眼复核」的成本。
- **百炼 `wanx2.1-imageedit` 绿幕重绘（ADR-0015 的原方案）**：生成式重绘有改动衣物本身的风险，对「衣橱作为推荐真源」不可接受（见背景 2）。已退役。
- **remove.bg**：效果顶级但订阅贵（$9/月起），自用不划算。
- **rembg 自托管**（开源 BiRefNet/U2-Net）：onnxruntime 原生库 + 模型（u2net 170MB、BiRefNet 900MB+）远超微信云函数包体上限，且无外置服务器。
- **硅基流动直连**：标准模型广场无背景移除/图像编辑模型（已核实 2026-09）。
- **Qwen-Image-Edit（硅基流动 0.3 元/张）**：同属生成式重绘，同样有改衣风险，且更贵。

## 复核：与阿里云视觉智能「商品分割 / 服饰分割」横向对比（2026-09-10 用户提问触发）

用户问：「走视觉智能开放平台的商品分割也能达到同样的真抠图效果？与 GoodsMatting 相比哪个更有优势？开通 COS 还要按量收费和定时清理。」
—— 借此把当时没细比的阿里方案补上，避免「选完就没人再问为什么」。（数据源：阿里云 OpenAPI 文档 + 2023-08-30 分割抠图调价公告，2026-09-10 核对）

**结论一：三家都是「真抠图」，效果同级。** 阿里 `SegmentCommodity` / `SegmentCloth` 与腾讯 GoodsMatting 都输出 **4 通道带 alpha 的透明 PNG**，属同一类能力，都能达到「不重绘、不改衣物本身」的目标。所以 ADR-0015 当初「只有 GoodsMatting 能真抠图」的隐含前提不成立——**可选项一直有两个**。

**结论二：决定性差异在输入上限，不在价格。**

| 维度 | 阿里 商品分割 | 阿里 服饰分割 | 腾讯 GoodsMatting |
|---|---|---|---|
| 结果形态 | 4 通道透明 PNG | 4 通道透明 PNG（可按品类） | 4 通道透明 PNG |
| 按量单价 | 0.002 元/次 | 同属分割抠图类目（计费页未单列） | **0.01 元/次** |
| 免费额度 | 单类目包 10,000 点 = **13,333 次**，首次 0 元试用，**有效期 1 年** | 同上 | **1,000 次 / 2 个月** |
| **输入大小** | **≤3 MB** | **≤3 MB** | **≤32 MB** |
| **输入分辨率** | **< 2000×2000 px** | **50×50 ~ 3000×3000 px** | **宽高 ≤50,000 px**，总像素 ≤2.5 亿 |
| 输出形式 | 临时 URL，**30 分钟过期**，须即刻下载 | 同左 | 响应体**直接返回二进制** `image/png` |
| 账号/开通 | 复用已有阿里云账号（与百炼同账号），开通「分割抠图」+ 建 AccessKey | 同左 | 需腾讯云账号 + COS 桶 + 绑数据万象 + 开「AI 内容识别」 |
| 小程序直调 | 官方支持 | 官方支持 | 经云函数（本方案） |
| 地域 | 仅上海 / 深圳 | 华东2（上海） | — |

价格看着差 5 倍，但**在自用体量下这是几毛钱的事**，不构成决策依据。真正要命的是 **3 MB / 2000 px 的输入卡点**：手机相册原图普遍 3000×4000、3–5 MB，走阿里就**必须先在云端或前端压缩**——多一个真机调参环节，且缩图会损失细节（针织毛边、细肩带、蕾丝边缘的抠图质量首当其冲）。腾讯的 32 MB / 50000 px 意味着**原图直传、不缩不裁**。

输出形态同理：腾讯在响应体里直接给 PNG，云函数一次 `uploadFile` 入库；阿里给的是 **30 分钟过期的临时 URL**，还得再 `https.get` 下载一跳——多一跳就多一个失败点。

**结论三：COS「按量收费 + 定时清理」的顾虑不成立。** 因为走的是 **detect-url 模式，图片根本不进 COS**：
- COS 桶可以**永远是空的** → 存储费 0、请求费 0、流量费 0（桶本身不收费，只对存储量/请求/流量计费）；
- **不需要任何定时清理任务**——清理的前提是「有垃圾要清」，这条链路不往桶里写任何东西，连垃圾都不产生；
- 唯一支出是 GoodsMatting 调用费 0.01 元/次，且前 1,000 次免费。
用户担心的那个问题，是「把图存进 COS」才会有的；本方案没走那条路。

**结论四：切换已无收益。** 腾讯这条路已经落地（云函数 + 签名 + 错误分类 + 单测全部完成），切阿里反而要重做：阿里 RPC 风格签名、3 MB/2000 px 压缩链路、30 分钟 URL 的即刻下载。**为了省 0.008 元/次去重做一遍，不划算。**

**结论五（新增候选，记为未来事项）**：阿里 **服饰分割 `SegmentCloth`** 的品类集合（外套 / 上装含内衬 / 裤装 / 裙装 / 帽子 / 鞋子 / 包包）几乎与本项目 `CAT_ORDER`（内搭/外套/长裤/短裤/裙装/帽子/鞋/包/配饰）一一对应，且**额外返回服饰类别识别结果**（tops / pants / skirt / shoes / bag / hat）。若将来想做「上传后自动预填品类」，这条路是现成的——届时再评估，本 ADR 不改现有决策。

## 后果

- **新增云函数 `mattingGoods`**（取代 `mattingAI`，云函数总数仍 7 个），接口 start/poll。
- **新增凭证**：`COS_SECRET_ID` / `COS_SECRET_KEY` / `COS_BUCKET`（形如 `xxx-1250000000`）/ `COS_REGION`（默认 `ap-shanghai`）→ `mattingGoods` 云函数环境变量。**原 `DASHSCOPE_API_KEY` 随 mattingAI 退役作废。**
- **退役清单**（已删，备份在 `.workbuddy/backup/2026-09-10-retired-matting/`）：
  - `pages/upload-item/matting.js`（客户端色键纯算法）
  - `dev/matting.test.js`（色键守卫）
  - `cloudfunctions/mattingAI/`（整目录：index.js / lib/parse.js / dev/mattingai.test.js / package.json / config.json）
  - `utils/api.js` 的 `mattingAI` 导出 → 换成 `mattingGoods`
  - ⚠️ 云端的 `mattingAI` 云函数**需用户在云开发控制台手动删除**（删本地源码不会删云端已部署实例）。
- **queue 状态机不动**：抠图仍发生在 `bg-removing` 环节内部，成功 `markBgDone`、失败 `markBgFailed`，`pngPath` 改记透明 PNG 的**云存储 fileID**（`<image src="cloud://…">` 原生支持）。前端从「本地色键出 PNG」换成「云端 GoodsMatting 出 PNG」，外部件状态机完全一致。
- **失败语义更诚实**：不再有 AI 兜底，失败就是失败，给「重新抠图 / 用原图继续」。失败弹窗按 `retryable` 分岔——不可重试的（欠费/未开通/签名/权限）明说「重抠也不会好，需先在腾讯云侧处理」，不诱导用户空转。
- **成本结构变化**：从「大头免费（色键）+ 难图 0.14 元（百炼 wanx2.1-imageedit 价）」变成**每张都计费**，但单价极低：GoodsMatting **0.01 元/次**（2023-12-01 起改用「通用抠图」计费项 0.02 元/次 + 抵扣比例 2:1 折算；0.14 元是调价**前**的旧价，见下方勘误），免费额度 **1000 次 / 2 个月**（一次性发放，比百炼的 500 张更多）。自用体量下免费额度完全够用，用尽后按 0.01 元/张。
- **新守卫**：`cloudfunctions/mattingGoods/dev/cossign.test.js`（COS 签名，24 断言）、`cloudfunctions/mattingGoods/dev/parse.test.js`（错误分类，25 断言）；`dev/upload-entry.test.js` 断言已从「AI 兜底接线」改为「mattingGoods 接线 + 旧链路已退役」。
- **残余风险**：`detect-url` 依赖微信云存储临时链接在抠图期间有效——`getTempFileURL` 的临时链接有时效，故必须**拿到即用**（代码里同一次调用内完成），不能缓存链接。

## 勘误（对 ADR-0015 的复核 —— 含对本 ADR 初稿的自纠）

ADR-0015「备选被拒」首条写：*「腾讯云数据万象 GoodsMatting（0.01 元/次，电商级）：与微信云开发存储跨账号体系，COS 绑定/detect-url 时效需实测，接入风险高于收益；保留为未来备选。」*

复核结论：

1. **价格：ADR-0015 写的 0.01 元/次是对的。本 ADR 初稿曾把它「更正」为 0.14 元/次，该更正是错的，现予撤销。**
   依据腾讯云《关于数据万象商品抠图价格调整的公告》：自 **2023-12-01 00:00:00** 起，商品抠图不再按「商品抠图 0.14 元/次」单独计价，改用「**通用抠图（通用计费项）0.02 元/次 + 抵扣比例 2:1**」——即 2 次商品抠图折算 1 次通用抠图用量，**实际 0.01 元/次**（公告计费示例：上传 10 张图 = 10×0.02/2 = 0.1 元）。「0.14 元/次」是调价**前**的旧价。免费额度 1000 次 / 2 个月（一次性发放）。
   教训：只看到「原计费标准 0.14 元」就当成现价，漏读了同页的「调整后计费标准」——**改价公告要整页读完，别只截取自己预期的那一半**。
2. **风险判断被推翻**：ADR-0015 把「跨账号体系 + detect-url 时效」当成主要接入风险。实测这两点都不构成阻塞——detect-url 模式让 COS 桶可以保持空置（图片不必迁入 COS），微信云存储仍是唯一真源；时效问题只需「拿到临时链接即用」即可规避。真正的风险反而在 ADR-0015 自己选的方案上（生成式重绘改衣）。

**结论**：ADR-0015 的绿幕重绘方案整体作废，本 ADR 取代之。ADR-0015 保留为历史留档（记录「为什么一度排除了 GoodsMatting」）。
