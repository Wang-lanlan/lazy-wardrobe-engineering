# ADR 0010：季节判定改由「季节+温度」联合驱动，并对推荐结果做硬校验

- **日期**：2026-09-02
- **状态**：已接受并实现（含 2026-09-02 二次修订：纯温度→季节+温度联合驱动）
- **相关**：ADR 0008（双轨溯源）、ootd-outfit 技能 `references/search-strategy.md`

---

## 背景

使用者反馈：「昨天 25~31℃，推荐搭配里却有长款风衣 + 牛仔裤，明显不符合天气。」

代码核查后确认**四个独立缺陷叠加**：

### 缺陷 1：季节来自日历，不是气温

`cloudfunctions/aiRecommend/lib/recommendCore.js:32-38`：

```js
if (m >= 3 && m <= 5) return '春夏';
if (m >= 6 && m <= 8) return '夏秋';
if (m >= 9 && m <= 11) return '秋冬';
return '春夏'; // 12/1/2 冬，无独立冬标签，归入春夏
```

**最后一行是倒错 bug**：12/1/2 月归入「春夏」。而 `brain.json` 的案例季节分布是
**春夏 0 条 / 四季 1 条 / 夏秋 7 条 / 秋冬 2 条**——真·冬天（1 月）筛下来只剩 1 条「四季」案例。

**所以「冬天生成夏天搭配」不是可能，是必然。** 9 月同理：日历判「秋冬」，
注入秋冬案例，而实际气温可能仍在 30℃ 以上。

### 缺陷 2：天气只是「告知」，不是「约束」

`promptBuilder` 里天气只渲染成一行文本：

```
当前天气：深圳 31℃ 晴
```

**没有任何硬性温度规则。** 对比 `ootd-outfit` 技能 `SKILL.md` 明确写着的硬性检查项：

> - 温度是否匹配（查到的温度 > 26℃ 不派外套，< 15℃ 必须有外套）

**这条规则从未被搬进小程序。** 技能有、小程序没有，是两套实现之间的能力落差。

更糟的是兜底文案 `未提供天气，请按当前季节和常规气温判断`——定位失败时
反而**强化缺陷 1**（回退到按日历季节判断）。

### 缺陷 3：案例的季节标签在推波助澜

9 月 → season=秋冬 → `pickCases` 注入
`case-beautyway-beige-trench`（beautywaymag《14 Stylish Korean Fall Outfits》米白风衣 · 休闲 · 秋冬）。

**这是「长款风衣」的直接来源之一**：案例带具体单品与配色逻辑，是具体信号；
温度只是一行抽象数字。LLM 必然跟具体走，温度被压过。

### 缺陷 4：用的是实况温度，不是预报

`cloudfunctions/getWeather` 调高德 `extensions=base`，只返回**实况**，
`live.temperature` 是单个当前温度，**不是 25~31 这种区间**。

后果：早上 8 点拿到 22℃ → 派外套 → 中午 31℃ 热死；晚上按 28℃ 推荐 → 早上冻死。
**穿衣决策是早上做的，针对的是出门后的一整天，而实况温度只代表「说话这一刻」。**

要拿到预报区间需改用 `extensions=all`（返回 `daytemp` / `nighttemp`）。

## 决策

### 1. 温度档位取代日历季节

新增纯函数 `tempBand(highTemp)` → 厚度档位，用档位筛选案例、约束候选单品，
**不再用月份推导季节**。`getSeason()` 仅修正 12/1/2 月的倒错（归入最冷档），
**目前仍用于案例筛选（case 的 scene/season grounding）的兜底**——
案例按日历季节注入的逻辑保留（详见第 6 节「实施状态」中关于案例温度过滤的取舍）。

### 2. 前置过滤：不让不合季的单品进入候选

**⚠️ 实施位置修订**：原 ADR 写「在 `pages/recommend/recommend.js` 过滤」，
但小程序页面无法 `require` `cloudfunctions/` 下的代码（`cloudfunctionRoot` 不参与小程序打包），
故实际落地在 **`recommendCore.js`（云函数）**：组装 prompt 前先按档位过滤候选单品，
**LLM 根本看不到风衣，自然不会派它**。档位信息由云函数算好后随推荐结果返回，前端只展示。

选它而不是「生成后重配」的理由：零额外 LLM 调用、零延迟、零成本，且从源头杜绝。
过滤是代码校验，不依赖 LLM 自觉。**这与 ADR 0008 的 inspoId 白名单是同一个思路：
把「希望它遵守」变成「它没法不遵守」。**

过滤分三层（`recommendCore`）：
- ① `isSeasonAllowed`：按单品 `season` 标签（四季 / 春夏 / 春秋 / 秋冬）判断；
- ② `isCategoryForbidden`：档位的「硬排除品类」（炎热档 `forbidCategories:['外套']`），
  **不依赖 season 标签是否准确**——风衣被误标成「春秋」时，炎热档仍靠品类拦得住；
  且细化为「只禁保暖型外套」，放行带 `薄/轻` 标签或 `season=春夏` 的轻薄外套（见第 6 节）。
- ③ `isSleevelessForbidden`：联合闸门①——冬季（日历）且 `low < 20` 时禁短袖/无袖内搭
  （由 `band.forbidSleeveless` 驱动），解决纯温度在冬季大温差天误派短袖的问题。
- 兜底：过滤后候选池为空（极端：衣橱全是过季件）则退回全量，交给 coatRule 约束。
- 解析阶段 `validIds` 也改为以过滤后的 `safeItems` 为基准，幻觉出的过季 id 会被二次丢弃。

### 3. 把 ootd-outfit 的硬规则搬进 promptBuilder

> 温度 > 26℃ 不派外套，< 15℃ 必须有外套

并把兜底文案从「请按当前季节」改为「请按温度档位 X 判断」。

### 4. 档位表（**待使用者校准**）

以下为初版建议，按**当天最高温**划分。示例用户（已脱敏）偏瘦体型通常更怕冷，
档位可能需要整体下调 2-3℃，**需由使用者确认后写入**。

| 最高温 | 允许的季节标签 | 外套 |
|---|---|---|
| ≥ 28℃ | 春夏、四季 | 禁止 |
| 23–27℃ | 春夏、四季、春秋 | 可选 |
| 18–22℃ | 春秋、四季 | 建议有 |
| 12–17℃ | 秋冬、春秋、四季 | 必须有 |
| < 12℃ | 秋冬、四季 | 必须有厚外套 |

### 5. 天气改取预报区间

`getWeather` 改用高德 `extensions=all`，取 `daytemp`（白天温度）作为档位判定依据，
`nighttemp` 用于「早晚温差大」的 tip 提示。**实况温度不再作为搭配依据。**

### 6. 二次修订：季节+温度联合驱动（2026-09-02）

使用者二次追问：「冬天（昼夜温差大）某天冲上 28℃，也不能穿短袖啊，是不是应该季节+温度联合驱动？」

**确认：纯温度驱动在冬季大温差天会翻车。** 只按 `high` 判档位，冬季某天 high=28 → 判「炎热」→
禁外套 + 派短袖；但该天 `low` 可能只有 12℃，早晚穿短袖会冻僵。使用者 166/45 偏瘦更怕冷，单看高温更危险。

**修订为联合驱动**：温度是「极值硬约束」，季节是「边际情境修正」，两者各管一段：

- **外套** → 由 `high` 决定（≥28 不派保暖型外套）。这部分原 ADR 正确，28℃ 中午穿风衣确实傻。
- **基础内搭袖长** → 由 `season`（日历）+ `low`（最低温）决定。冬季且 `low < 20` → **禁短袖/无袖**，
  长袖打底 + 可叠薄开衫应对早晚。阈值 `SLEEVE_LOW=20` 由使用者确认。
- **基础单品季节适配** → 保留原温度档位的 `allowSeasons` 过滤（不改用日历季节，否则换季月份会系统性错配）。

新增两个代码闸门（均在 `lib/tempBand.js`）：

- `band.forbidSleeveless` = `(season==='秋冬') && (low != null && low < 20)`，驱动 `isSleevelessForbidden(item, band)`；
- `isCategoryForbidden` 细化为「**按保暖度**禁外套」：炎热档只禁保暖型外套（`season=秋冬`，或带
  `厚/加绒/毛呢/保暖/羽绒` 标签），放行薄款（带 `薄/轻` 标签、或 `season=春夏/春秋/四季` 且无保暖标签）。

### 6.1 三次修订：外套按保暖度，不按品类一刀切（2026-09-02 收尾）

使用者二次追问收尾：「冬季大温差(28/12)只需要砍掉厚风衣，薄款（春秋款）外套应该保留才符合逻辑。」

**原实现把 `forbidCategories:['外套']` 一刀切**——无论厚薄，炎热档整个「外套」品类被锁死，
导致 28/12 的**春秋款风衣（薄）也被误杀**，与诉求相悖。

**修订为按保暖度判定**：风衣/西装本身可厚可薄，必须看 `season=秋冬` 或保暖标签，而非品类。
于是「厚风衣砍、春秋款风衣留」自然成立。同时新增 `isItemAllowed`（三层过滤组合入口）：
**炎热档的外套不套用基础 `allowSeasons` 过滤**——否则 28/12 的春秋款风衣会被 hot 档
`allowSeasons=['春夏','四季']` 误杀（春秋不在其中）。

**修正后冬季大温差天(28/12, 秋冬)端到端结果**（mock LLM 故意想选全部）：
春秋款风衣 ✅（薄，保留）｜ 厚风衣 ❌（秋冬保暖型，砍）｜ 薄开衫 ✅（应对早晚）｜
秋冬厚毛衣 ❌（28℃ 中午过热，温度档位过滤）｜ 长袖针织 ✅（长袖打底）｜ 短袖 ❌（联合闸门①禁）。
→ 长袖打底 + 薄开衫/春秋款风衣，全天不冻不闷，自洽。

**盛夏(31/26, 夏秋)**：春秋款风衣 ✅（轻薄件保留）｜ 厚风衣 ❌｜ 短袖 ✅｜ 薄开衫 ✅。正常夏装。
⚠️ 顺带行为：炎热档对「薄款/春秋款外套」一律放行（含盛夏），因为这是「保暖度」判定而非「夏天不穿外套」判定；
若希望盛夏更严格（31℃ 连薄外套都不派），需另加「炎热档非冬季时连轻薄外套也禁」规则，待使用者确认。

## 取舍

**放弃的**：
- 用月份推导季节（简单，但在换季月份系统性出错）
- 生成后重配（要二次调用 LLM，成本与延迟翻倍，且仍依赖模型自觉）
- 用实况温度（只代表当下，不代表出门后的时段）

**换来的**：
- 换季月份（3/6/9/11 月前后）不再系统性错配
- 真·冬天不再按春夏推荐
- 过滤是代码执行，结果确定，不受模型波动影响

**代价**：
- 温度档位会缩小候选池（31℃ 时秋冬单品不可见）—— 这是**期望行为**，不是缺陷
- 档位边界（如「春秋」单品在 27℃ 算不算）存在模糊地带，需按体感校准

## 实施顺序

1. `lib/tempBand.js` + 单测（纯函数，可离线断言）→ 2. 校准档位表（等使用者）
3. `getWeather` 改 `extensions=all` → 4. `recommend.js` 前置过滤
5. `promptBuilder` 加硬规则 + 改兜底文案 → 6. 修正 `getSeason()` 的 12/1/2 倒错

第 2 步阻塞第 4 步，其余可并行。

### 数据标签陷阱（务必读）

前置过滤**依赖单品 `season` 标签准确**。使用者衣橱里的长款风衣被标成了 **`春秋`**，
而「春秋」在偏热档（23–27℃）是允许出现的——所以 **23–27℃ 时那件误标风衣仍会冒出来**
（炎热档 ≥28℃ 已被品类硬排除兜住，故 31℃ 不会）。

**修正动作**：把那件长款风衣（及任何厚外套）的 `season` 改成 **`秋冬`**，它就会在
23–27℃ 被正确过滤掉，只在 12–17℃ / <12℃ 才回归。改标签在 App 内编辑单品即可
（注意：云端 54 件是真源，本地 `seed/items.json` 与 `cloudfunctions/seedImport/items.json`
是导入副本，已导入后改这两份不生效，需改云端）。

### 防晒外套例外（功能型外套 ≠ 保暖/装饰性外套）

使用者指出：炎热档 `forbidCategories:['外套']` 会无差别排除所有「外套」品类，
而防晒衣作为功能型外套，恰恰要归在「外套」下，导致 30℃ 大太阳天反而被藏起来——
与「禁止风衣」误杀同一批。

**修正**：单品新增 `tags` 功能标签。带 `tags:['防晒']`（或字符串 `'防晒'`）的外套，
在 `isCategoryForbidden` 层被例外放行。炎热档 `coatRule` 文案同步改为
「禁止保暖/装饰性外套（风衣、西装、夹克、毛呢、厚开衫），但功能型防晒衣可以派」。

- 防晒衣仍受 `season` 约束：本就该标 `春夏`/`四季`，炎热档自然通过；若误标 `秋冬` 仍会被 `isSeasonAllowed` 挡（数据正确性问题，不在品类层豁免）。
- 端到端验证：high=31 时防晒衣 ✅ 出现、风衣 ❌ 被拦；high=26（偏热档允许春秋）时两者 ✅。

**使用约定**：衣橱里加防晒衣时，`category` 仍填「外套」，`tags` 加 `['防晒']`，`season` 标「春夏」或「四季」。

### 案例温度过滤未做（取舍）

`pickCases` 仍按**日历季节**注入案例（未加温度档位过滤）。原因：案例季节词表含
「夏秋」，而 `tempBand` 的 `allowSeasons` 词表是 `{春夏,四季,春秋,秋冬}`，**没有「夏秋」**——
若按档位过滤会把所有「夏秋」案例一刀切掉，破坏案例 grounding。

实际影响有限：案例只是「灵感来源」（具体单品不在衣橱候选池里），即便注入了风衣案例，
风衣单品已被前置过滤挡在候选外，LLM 最多把它写进 `wish`（建议购买），不会「派你穿」。
若未来要彻底让案例也随温度收敛，需先把案例/单品的季节词表统一（补「夏秋」到各档 allowSeasons）。

## 何时重开

- 使用者反馈「按这个档位还是偏冷/偏热」→ 调整档位表，不影响架构
- 常驻城市换季温差长期超过 15℃（早晚）→ 需要引入「分层建议」而非单一档位
- 出现「过滤后候选池太小导致三套搭不出来」→ 放宽边界档位，或允许跨档并在卡片上标注
