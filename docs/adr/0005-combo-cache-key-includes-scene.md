# ADR 0005：组合缓存键包含场景

- **日期**：2026-08-30
- **状态**：已接受（同日改码落地）
- **相关**：ADR 0004（成本护栏）、CONTEXT.md「组合」词条

---

## 背景

「组合」是上身图的生成与计费单位。初版实现里，缓存键**只由单品集合决定**：

```
key = md5( 单品id 排序后拼接 )
```

但代码同时存在一个**自相矛盾**的地方——缓存记录里存了 `scene` 字段，而场景在提示词里会显著改变画面：

| 场景 | 画面 |
|---|---|
| 上班 | 简洁办公室、柔和窗光 |
| 休闲 | 林荫街道、午后日光 |
| 约会 | 暖调咖啡街角、黄金时刻 |
| 旅行 | 阳光广场、明亮自然光 |
| 居家 | 明亮室内、柔和日光 |

**后果**：同一套衣服，先按「上班」生成一张，之后改成「旅行」再点——拿到的还是那张办公室背景的旧图，而且会提示"已生成过，本次不扣费"，用户以为生效了。场景被存进去了，却从未参与判断。

## 决策

**组合 = 单品集合 + 场景。**

```
key = md5( 单品id 排序后拼接 + '#' + 场景 )
```

二者任一变化即视为新组合，重新生成并计费。

## 取舍

**放弃的**：

- **成本上限被抬高**：同一套衣服最多可能生成 5 张（5 个场景），最坏情况成本 ×5
- 换场景时的"免费复用"

**换来的**：

- **语义自洽**：场景真正影响画面，就该真正参与计费与缓存判定
- 用户看到"已生成过"时，确实就是同一套衣服、同一场景，不会有"明明换了场景怎么图没变"的困惑

**备选方案（未采用）**：把 5 个场景映射到 2 个氛围档（上班/约会=正式，休闲/旅行/居家=日常），成本控制在 2 倍以内。
*未采用的理由*：氛围档是个新建的抽象概念，需要额外维护映射表，而场景本身已经是个稳定枚举。为了省一点钱引入一层间接，不值得。

## 已知副作用

**改键后，此前生成的旧缓存记录全部成为孤儿**——它们的键不含场景，永远不会再被命中，但仍占用云存储与数据库记录。

影响很小（历史生成量极少），且**不影响任何功能**。若日后要清理，可按"缓存记录中的场景字段与期望不符"或"创建时间早于改键日期"筛选删除。

## 何时重开

- 发现同一套衣服跨场景生成多张，月支出明显上升 → 退回"仅单品集合"或改用氛围档
- 用户反馈换场景后图没变 → 检查缓存键是否被误改回不含场景的版本
