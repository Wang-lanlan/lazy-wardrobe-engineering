# ADR 0007：统一「大脑」——小程序与 ootd 技能共用韩系规则 + 案例库，并在降本前提下对齐网页版韩女搭配

- **日期**：2026-08-31
- **状态**：待实施
- **相关**：ADR 0001（小程序云为唯一真源）、ADR 0003（可插拔生图 provider）、ADR 0004（按需生图 + 组合缓存 + 月额度）
- **起因**：使用者提问「小程序版搭配推荐是不是没用我的 ootd 技能？如何既兼容网页版那样形成韩女搭配，又降低成本？」

---

## 背景

### 事实核查：小程序确实没用 ootd 技能（已由代码确认）

| 维度 | 网页版 / `ootd-outfit` 技能 | 小程序 `wardrobe-miniapp` |
|---|---|---|
| 调用入口 | WorkBuddy 会话里跑技能 | 云函数 `aiRecommend` 直连大模型 |
| 韩系素材来源 | **实时 WebSearch** 抓韩国博主/明星私服（三级降级 + `freshness:m3`） | **无检索**，纯靠大模型内部知识 |
| 规则来源 | `references/style-guide.md`（8 章完整规则库） | `aiRecommend/index.js` 内**硬编码的 6 条精简版 prompt** |
| 衣橱来源 | `references/wardrobe.md`（技能自带） | 云数据库 `items` 集合 |
| 出图 | 每次 **3 张 AI 上身图** | 默认拼贴（¥0），**按需**点「看上身效果」才生 1 张 + 月额度 + 组合缓存 |

两边已**分叉**：规则两份、衣橱两份、案例一份有一份无。

### 差距的真正根源

不是规则写得差，是**缺了"案例 grounding"这一层**。

- 无案例时，模型输出教科书式通配：*"米白阔腿裤 + 炭灰针织 + 乐福鞋，松紧对冲"* —— 没错，但谁都能编，韩味淡。
- 有案例时，输出变成可抄的具体穿法：*"参考 1017kk 本周白开水穿搭：燕麦开衫当披肩、内搭白 T 领口叠露、下身微喇水洗蓝，亮色只放堆堆袜"*。

**韩女感恰恰来自"这是抄了某个真实博主某一套"的具体性，而不是规则本身。**

### 核心矛盾

网页版的 WebSearch 在 WorkBuddy 会话里是内置工具（免费）；但搬到云函数里必须接**付费搜索 API**。所以「完全兼容网页版的实时检索」= 每次推荐都烧钱，与「降本」直接打架。

## 决策

### 1. 案例供给：预烘焙案例库（放弃每次实时检索）

我用会话 WebSearch（免费）检索韩国私服案例，洗净成结构化条目，随「大脑文件」发布。运行时**零检索成本**。

*理由*：韩系街头风格不以周为单位变化，换季刷新足够。把「每次推荐都检索」降级为「批量检索一次、多次复用」，是本次降本的核心杠杆。

### 2. 大脑单一真源：`brain.json` 托管静态 URL + 云函数拉取缓存

`brain.json` = **完整韩系规则库**（8 章）+ **案例库**，托管到一个我可直接覆盖的稳定静态 URL（CloudStudio 静态部署）。

云函数 `aiRecommend` 冷启动 `fetch` 一次 → 内存缓存 → 并落一份到云存储做兜底。

*为何不放云数据库*：放库能免部署，但「谁写库」需要额外管道（我无法在会话里直接写云库，得靠脚本或触发云函数）。托管静态 URL 少一层，且刷新由我覆盖文件完成，**使用者全年 0 操作**。

*为何不烤进云函数代码*：刷新需要重新上传部署云函数，一年 4 次——使用者明确嫌麻烦，已否决。

**三级降级**（与 ootd 技能检索降级同构）：

1. `fetch` 静态 URL 拿最新 `brain.json`
2. 失败 → 读云存储兜底副本
3. 再失败 → 用代码内精简规则（现状 6 条）继续推荐，**不阻断功能**

### 3. ootd 技能指向同一份 `brain.json`，终结规则漂移

技能 `references/` 改为读同一份大脑文件。概念上只有一份规则、一份案例，两个消费方。

### 4. 刷新：默认我定期覆盖 + 小程序「刷新灵感」按钮自助补新

- **主力**：我换季重跑检索覆盖 `brain.json`（你 0 操作）。
- **自助**：小程序加「刷新灵感」按钮 → `refreshCases` 云函数调 **Tavily** 检索 → 写案例 → 下次推荐生效。

*为何敢做按钮*：Tavily **免费档 1,000 credits/月**，basic 检索 = 1 credit，一次刷新约 3 credits → 免费档可刷约 333 次/月。自用一个月点 1–4 次，**实际 ¥0**。超出才走 PAYG $0.008/credit（≈¥0.17/次刷新）。

*已排除的方案*：
- SerpAPI —— 订阅制（$25/月起）、无按量付费、月末清零，零散自用等于白交月租。
- 硅基流动 —— 无原生联网搜索 API，走第三方代理按天收费，不划算。

### 5. 输出新增 `inspo` 字段：方案必须标注"抄了谁"

`aiRecommend` 返回结构增加 `inspo`（本套借鉴的案例来源 + 可迁移点），推荐卡片展示"参考了谁"。

*理由*：这是把案例 grounding 的价值**交付到界面上**的唯一方式。没有它，案例只在 prompt 里空转，用户感知不到韩味从哪来。

### 6. 出图策略不变：按需 + 月额度 + 组合缓存

**绝不退回网页版"每次 3 张图"的打法**——那是网页版最大的成本项，也是小程序已经比网页版更省的地方。

## 数据流

```
[会话] 我 WebSearch 韩国案例 ──写盘──> brain.json ──CloudStudio 静态部署──> 稳定 URL
                                                                              │
小程序 aiRecommend 冷启动 ──── fetch ────────────────────────────────────────┘
        │  失败 → 云存储兜底副本 → 代码内精简规则（三级降级）
        ├─ 注入完整韩系规则(8章) + 按 场景/季节 匹配的 top N 条案例
        └─ 1 次 LLM 调用 → 3 套方案（含 inspo 来源标注）

[小程序] 点「刷新灵感」 ──> refreshCases 云函数 ──Tavily(免费档)──> 新案例 ──> 写云存储/云库
[ootd 技能] ──读同一份 brain.json──> 网页版出方案（与小程序同源同味）
```

## `brain.json` 结构约定

```json
{
  "version": "2026-09-autumn",
  "updated": "2026-08-31",
  "rules": {
    "core":        "核心美学：干净、层次、松弛…",
    "color":       "大块中性色 + 小块点亮色…",
    "silhouette":  "松紧对冲对照表…",
    "material":    "软硬对冲…",
    "layering":    "叠穿三处露一处…",
    "pitfalls":    "避坑清单…",
    "sceneTable":  "场景适配表…",
    "bodyOpt":     "身材优化（含示例用户画像，已脱敏）"
  },
  "cases": [
    {
      "id": "c-1017kk-001",
      "season": ["秋"],
      "scene":  ["休闲", "约会"],
      "source": "博主名 / 媒体名 + 原始链接",
      "items":  "上装、下装、鞋、外套分别是什么（不接受空话）",
      "logic":  "配色怎么配、版型怎么对冲、层次怎么叠",
      "transferable": "普通人能直接抄的那一点"
    }
  ]
}
```

**注入策略**：按 `scene` + 当前季节筛出 top 3–4 条案例注入，避免 token 膨胀。大脑文件体积控制在 **20–40KB**。

**案例质量红线**（沿用 `search-strategy.md`）：四项缺一即丢弃（来源 / 具体单品 / 可借鉴逻辑 / 可迁移点）；**禁止编造博主名、明星名或链接**。

## 成本终版对比

| 项 | 网页版 ootd | 小程序（本方案后） |
|---|---|---|
| 韩系规则 | 完整 8 章 | **完整 8 章（同源）** |
| 案例 | 每次 3 次实时 WebSearch | 预烘焙库（**¥0 运行时**）+ 按钮自助刷（Tavily 免费档 **¥0**） |
| 出图 | 每次 3 张 AI 图 | 默认拼贴 ¥0，按需 1 张 ¥0.036–0.1 + 月额度 + 组合缓存 |
| LLM | 1 次 | 1 次（prompt 增加约 2k token，DeepSeek-V3 ≈ **¥0.005/次**，可忽略） |
| **刷新操作** | 每次会话自动 | **你 0 操作**（我覆盖，或点按钮自助） |

**结论**：质量对齐网页版，运行时成本 ≈ 网页版每次 3 张图打法的 **1/30 以下**。

## 取舍

**放弃的**：

- 每次推荐都拿到"当下这一秒"的韩国案例（改为批量预烘焙，时效性滞后 0–4 周）
- 案例存放的完全云原生（引入一个外部静态 URL 依赖）

**换来的**：

- 韩女搭配质量对齐网页版，且方案能说清"抄了谁"
- 运行时检索成本归零
- 规则与案例单一真源，终结小程序/技能两边漂移
- 刷新零操作

**为什么外部 URL 依赖可接受**：已有三级降级，URL 挂掉最多退化到现状质量，不会让推荐功能不可用。

**Tavily 的质量风险与预案**：Tavily 是通用网页搜索，对小红书/中文韩系解析文的覆盖可能弱于会话内 WebSearch。**首次完成后陪跑验证一次**：若案例太水，则把按钮降级为"只产出趋势词提示、不进主案例库"，主力仍是预烘焙库。

## 何时重开

- 使用者觉得方案"韩味"仍不够 → 检查案例注入条数是否不足，或案例质量红线放水了
- 静态 URL 频繁不可用 → 升级为云库方案（ADR 0007 决策 2 重开）
- Tavily 免费档不够用（月刷新 >300 次）→ 评估 PAYG 或换 Serper
- 大脑文件膨胀到显著拖慢冷启动 → 拆分按季节加载
