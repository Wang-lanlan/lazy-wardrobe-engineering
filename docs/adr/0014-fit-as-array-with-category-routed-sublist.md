# ADR-0014 · fit 字段从 string 升级为 string[] + 按 category 路由 sub-list

- 状态：采纳（2026-09-09，grill-me 追加轮拍板）
- 关联：docs/specs/0006-upload-item-page.md（决策 8）

## 背景

spec 0006 初版决策 8 把 fit 定为 9 项 flat 受控列表（修身/常规/宽松/oversize/短款/长款/紧身/直筒/A 字），隐含假设：fit 在所有品类语义一致。

grill 追加轮用户否决该假设，原话：

> 上下装分开，比如内搭有宽紧（修身/常规/宽松/oversize）、长短（露脐/常规/长款），裙子分连衣裙（短款/中长款/长款）、半身裙（短款/中款/长款）……每类单品都有不同的对应，而不是大杂烩。

后续两轮补丁继续差异化：长裤加拖地款、短裤/半身裙加超短款、鞋要先分鞋型（平板鞋/运动鞋/休闲鞋/高跟鞋/靴子），且高跟鞋走「跟高」、靴子走「筒高」——连「高跟鞋和靴子 fit 一样」的错误预判也被纠正。

## 决策

1. **字段形状**：`fit: string` → `fit: string[]`（标签数组，多维度并存，如 `["oversize", "长款"]`）
2. **新增 `FIT_BY_CATEGORY` 二级字典**：第一级 key = category，第二级 key = 维度名（宽紧/长短/版型/长度/跟高/鞋头/筒高…），value = 受控标签数组
3. **`canonicalFit(category, fitArray)`**：按 category 路由 sub-list 验证数组每个元素；返回 `{ fit, dropped }` 双字段（有损归一可追溯）。丢弃规则（标脏自证，不凭空造默认值——「回退维度首项」仅用于 UI 默认选中）：① 越界标签（品类词表无此标签）→ 丢弃；② 歧义标签（出现在多个维度，如「常规」同在内搭宽紧/长短）→ **固定归声明序首逻辑维度，仅当首维度已被占用才丢弃**（否则「修身/常规」的常规会静默滑进长短凭空造数据）；③ 条件维度依赖的亚类/鞋型未被保留 → 丢弃；④ 短标签是已保留长标签的子串（「高跟」⊂「高跟鞋」）→ 不单独占维度
4. **双列面板 fit 动态化**：fit 字段左侧列表由当前 category 驱动（内搭 → 宽紧+长短；裙装 → 亚类+长度；鞋 → 鞋型+跟高/筒高/鞋头）
5. **AI 约束**：`recognizeItem` SYSTEM prompt 限定 fit 只能输出当前 category sub-list 内的标签，可多标签
6. **无 fit 品类**：帽子/包/配饰的 fit 字段整体不出现（canonicalFit 返回空数组）；鞋类的鞋型标签（平板鞋/运动鞋/休闲鞋/高跟鞋/靴子）始终保留在 fit 数组中——下游条件维度路由依赖它——但平板鞋/运动鞋/休闲鞋无版型维度（不出跟高/筒高/鞋头）
7. **sub-list 全集**：以 spec 0006 决策 8 为唯一真源（本文档不复制，避免双真源漂移）

## 理由（trade-off）

1. **表达力**：flat list 无法表达「内搭同时有宽紧+长短两个独立维度」；标签数组是承载多维度的最小变更。
2. **语义准确**：fit 在不同品类的维度本质不同（内搭=宽紧/长短、长裤=版型/长短、鞋=跟高或筒高/鞋头）——品类路由让「加内搭不会看到鞋的选项」。
3. **亚类是天然两级结构**：裙装（连衣裙/半身裙）与鞋（高跟鞋/靴子）都需要先选亚类再选维度——与 category 本身的两级路由同构，心智一致。
4. **否决的备选**：
   - 强结构子对象 `{宽紧:'oversize', 长短:'长款'}`：最规整但所有消费方大改，且品类间 key 不齐（帽子无 fit）会导致 schema 碎片化。
   - 前缀字符串 `'内搭.宽紧=oversize'`：兼容旧 string 但 AI 难吐准、下游解析脆。
   - 沿用 string 只换列表：完全无法满足多维度需求。

## 后果

- **正面**：按品类出选项，AI 识别受 sub-list 强约束更准；用户调整面板所见即所得；为后续鞋型扩展（凉鞋/拖鞋等）预留了纯数据扩展点（加字典项即可，不动逻辑）。
- **负面 / 风险**：
  - **数据迁移**：旧 `fit: string` 按强分隔符切分成数组（不含空格——「A 字」不能切碎）；含受控词的自由文本（如「修身一点」）由子串扫描提取受控标签，原始串同时进 `dropped`（有损归一可追溯）；纯不可分割文本（如「韩系风」）置空数组并标脏——不猜、不硬归一。
  - **消费方同步（铁律三/六重灾区）**：`recommendCore` / `lookPrompt` / `caseGate.fitIntersects` / `slotMap.FIT_ALIASES`（若有）全部按 `(category, fit[])` 双键改；前端 item-edit / upload-item 同构一份。改一处漏一处 = 静默错位。
  - **版本盐**：fit 归一化结果变化会影响推荐/试衣 prompt——相关缓存键需随 `BUILD_TAG` 升级而失效（铁律一）。
- **可逆性**：字段形状变更不可轻易回退（旧数据已迁移成数组）；但 sub-list 内容易扩易缩——加品类/加标签均为低风险纯数据操作。
