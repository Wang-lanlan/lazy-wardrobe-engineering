# ADR 0001：小程序云为唯一数据真源，本地版本退役

- **日期**：2026-08-30
- **状态**：已接受（已执行，本地版不再维护）

---

## 背景

衣橱数据此前散落在**四处**，且互不同步：

1. 技能侧的 Markdown 清单（`ootd-outfit` 技能的 `references/wardrobe.md`）
2. `outputs/wardrobe.json`（静态网页的数据源）
3. `wardrobe-app/`（Node 可编辑应用，自带本地 JSON 存储）
4. 技能里 AI 生成的 54 张实物图

痛点不是"没有"，而是**分叉**：在网页上改了衣服，技能不知道；技能更新了清单，网页不认。

更致命的是本地网页版的**可达性**：它跑在本机 `http://<局域网IP>:8787`，依赖两台设备同网 + 电脑不关机。实测中先后踩到：

- 电脑休眠后后台服务停止 → 网页打不开
- 局域网 IP 变更（`10.129.182.1` → `10.62.243.1`）→ 之前存的书签全部失效
- 换网络环境需重新查 IP、重新放行防火墙

## 决策

**小程序云数据库成为衣橱的唯一真源。** 其余三处全部降级为历史留档，不再维护、不再同步。

- 本地 Node 版、静态网页版退役
- 54 张 AI 实物图**不迁入**云端（见 ADR 0006）
- 数据随账号走，与设备、网络、是否开机完全解耦

## 取舍

**放弃的**：

- 单机局域网访问的"零配置"便利（其实并不零配置）
- 本地大图存储能力（54 张图留在本地，云端按需补拍）
- 不依赖微信生态的可移植性

**换来的**：

- 换手机、换电脑、换城市，数据始终一致
- 手机原生入口（拍照补图、随时随地改）
- 免运维：不用管服务器进程、防火墙、IP

**为什么不选"两端双向同步"**：同步是分布式一致性问题，对单人自用项目是净负债。与其花力气让两份数据勉强一致，不如只留一份。

## 何时重开

- 需要把衣橱数据开放给第三方（如导出到别的 App）→ 届时加导出能力，仍以云为真源
- 微信云开发免费额度不够用且不愿付费 → 可评估自建，但需重新承担运维成本
- 需要脱离微信生态使用（如网页端分享给别人看）→ 届时以云端为源做**只读**导出，不做双向同步
