# ADR 0009：单品实物图必须进入生成链路，否则一切生成图都是想象

- **日期**：2026-09-02
- **状态**：已接受
- **相关**：ADR 0003（可插拔 provider）、ADR 0004（按需生图）、ADR 0008（flat lay）

---

## 背景

使用者反馈：「比如牛仔外套单品，AI 生成的图中的牛仔外套并不是我衣橱中的那件。」

代码核查结果，三层原因：

### 1. 单品实物图从未进入生图链路（直接原因）

`genLookImage/index.js` 取单品时拿到的是完整 doc（含 `img` 字段），但
`lookPrompt.buildPrompt()` 只消费 `name` / `color` / `material` / `fit` / `category`
五个**文字**字段，拼成一句描述后交给文生图模型：

```
蓝牛仔材质牛仔翻领外套（短款/常规）
```

模型没有任何关于这件衣服的视觉信息，只能从训练数据里「想象一件符合这句话的牛仔外套」。
颜色深浅、水洗做旧、五金、口袋位置、衣长——全部由模型自行补全。

grep `cloudfunctions/genLookImage` 全文，唯一进入模型的图像是
`metaDoc.refImage`（用户人像参考照），**没有任何一处读取 `item.img`**。

### 2. 想送也送不了：54 件种子数据全部无图

| 文件 | 条数 | 有实物图 |
|---|---|---|
| `seed/items.json`（本地副本） | 54 | **0** |
| `cloudfunctions/seedImport/items.json`（云端真源） | 54 | **0** |

即使修好代码，当前也没有图可送。

### 3. 这是同一个病根的第三次发作

| 真实的东西 | 是否进入生成链路 |
|---|---|
| 检索到的韩女案例 | 否（ADR 0008 已记录） |
| 用户自己烘焙的规则库 | 否 |
| **衣橱单品的实物照片** | **否（本 ADR）** |

**这个产品里所有「真实的东西」都没有进入生成链路，进去的只有文字。**
因此生成的一切本质上都是模型对文字的想象。这不是 prompt 调优能解决的，是架构性的。

## 决策

### 1. 承认：ADR 0008 第 4 条在当前架构下无法兑现

ADR 0008 决定「上身图改为 flat lay，且只画用户自己的单品」。
**但 flat lay 走的仍是文生图，画出来的依然是模型想象的衣服，只是想象成平铺的样子。**
「只画自己的单品」这个约束在当前链路上没有技术手段可以兑现。

### 2. 唯一能让「图上的衣服 = 衣柜里那件」的路径是虚拟试衣（aitryon）

阿里云 `aitryon` 系列正是为此设计：`person_image_url` + `top_garment_url` + `bottom_garment_url`，
把真实服装平拍图穿到真人身上。这是 ADR 0003 预留的四个 provider 里唯一有价值的一个。

### 3. 但 `genByAitryon` 当前是空壳，四处硬伤

```js
input: { prompt, base_image_url: refUrl }   // 现状
```

| # | 问题 | 官方要求 |
|---|---|---|
| 1 | 参数名 `base_image_url` | 应为 `person_image_url` |
| 2 | **完全没有 `top_garment_url` / `bottom_garment_url`** | 必填，这才是「你的衣服」的入口 |
| 3 | 传了 `prompt` | `aitryon` 是试衣模型不是生图模型，`prompt` 无效 |
| 4 | `X-DashScope-Async: disable`，取 `res.output.results[0].url` | 官方要求 `enable`（异步），返回 `task_id`，须二次轮询 `GET /api/v1/tasks/{task_id}` |

另：`parameters` 应为 `{ resolution: -1, restore_face: true }`，不是 `{ n: 1 }`。

**结论：这个 provider 从未跑通过，也从未被调用过**（`PROVIDER` 默认 `siliconflow`，且 `WANX_KEY` 未配置）。

### 4. 服装图的硬性要求（来自官方文档）

`top_garment_url` / `bottom_garment_url` 必须是**服饰平拍图**：

- 单一主体且完整，背景干净，四周不宜留白过多
- 5KB ≤ 文件 ≤ 5M，150 ≤ 边长 ≤ 4096
- 仅支持 jpg / png / jpeg / bmp / heic，仅支持 HTTP/HTTPS 链接

这意味着**现有随手拍的衣物照片大概率不合格**，需要专门平拍。

## 取舍

| 路径 | 能否兑现「图上是我的衣服」 | 成本 |
|---|---|---|
| **拼贴**（直接用实物图） | 能，100% 真实 | 零生成成本，但需 54 件全部拍照 |
| **修好 aitryon 虚拟试衣** | 能，且是唯一能「穿在身上」的路径 | 需阿里云 key + 异步轮询改造 + 54 件平拍图 + 一张正面全身人像 |
| **文生图（现状 / flat lay）** | **不能，永远不能** | 便宜，但是幻觉 |

**放弃的**：用文生图产出「看起来像我的衣服」的图片——这条路技术上不存在。

### 5. 决策：拼贴为主 + 试衣小步试点（2026-09-02 使用者选定）

**拼贴是默认答案，试衣是可选增强。**

关键依据：拼贴是**渐进的**——`pages/recommend/recommend.wxml` 已有色块兜底
（`<image wx:if="{{it.img}}">` / `<view wx:else class="swatch" :style="background: colorHex">`），
54 件全无图也能跑，拍一件就真实一件，无需一次补齐。
而试衣是**全有或全无**：必须平拍合格才可用，两槽位上限又让它最多还原 6 件中的 2 件。

因此分工：
- **主链路 = 拼贴**：承担「用哪几件」，即 ADR 0008 定义的卖点。100% 真实（你的平拍图），6 件全有，但不穿在身上。
- **可选增强 = 试衣**：承担「穿起来什么样」，先以 10 件高频单品试点，
  通了就加个「看穿起来什么样」的按需按钮，不通也不影响主链路。
- **⚠️ 上身图引擎定论（2026-09-02 二次澄清）**：试衣路径的「AI 上身图」必须是
  **aitryon 图条件生成（把你的平拍图当 `top_garment_url`/`bottom_garment_url` 喂进去）**，
  **绝不是 Z-Image-Turbo 纯文生图**。`genLookImage` 当前默认走文生图（只吃文字不吃图），
  正是「牛仔外套不是我那件」的病根；要落地「真实外套进上身图」必须修 `genByAitryon`
  （补 garment URL、改异步轮询），把引擎从文生图切到 aitryon。
- aitryon **只有上装+下装两个槽**，外套/鞋/包/配饰进不去试衣图——故「6 件全是真实且穿在身上」一张图做不到，
  真实全量靠拼贴、真实上身靠试衣，各管各的（与使用者「单品实物要进 AI 上身图」的诉求一致，只是分两条管道实现）。
- 试衣试点**必须先核实**两笔账：aitryon 单价、异步轮询与云函数 timeout（当前 60000ms）的冲突

## 何时重开

- 54 件平拍图完成 → 可真正评估 aitryon 效果，再决定是否投入修复
- aitryon 修复后效果仍不满意 → 退回拼贴，并把「生成图」整体从产品里摘掉
- 出现支持多图条件的编辑模型（可一次吃多张服装图）→ 重新评估 flat lay 路径

## 修订

ADR 0008 决策第 4 条据此修订：flat lay 的前提是「单品实物图能进入生成链路」，
该前提已由本 ADR 证伪。在 aitryon 修复并验证之前，**「生成图」一律视为氛围示意图，
UI 必须标注，不得让使用者误以为是自己的衣服。**
