## 0. 一句话总纲

**可见的 AI 才是可被评判的 AI。** 整条链路只服务一件事：把你关注的韩国博主的穿法，
落到**你自己的衣柜**上，并且每一步都可以被验证——参考了谁、满足了什么约束、图是哪天哪版生成的，
全部有据可查。

支撑它的工程哲学只有一句，反复出现在每个环节：

> **把「希望 LLM 遵守的」，全部变成「它没法不遵守的」。**

温度不合时宜的单品？不是写进 prompt 求模型别用，而是**前置过滤让它根本看不见**。
博主思路？不是软文本让模型"参考一下"，而是结构化硬约束，**不满足就不得署名**。
AI 自报的灵感来源？不是信它，而是**白名单校验，编造就降级**。
这个哲学贯穿全链路，读后面每一节时请带着它。

## 2. 供给侧方法论：韩女穿搭怎么找、怎么入库

### 2.1 为什么需要案例库

最初的推荐是"教科书式通配"——8 章规则喂给 LLM，产出的是**正确但没灵魂**的建议：
版型对冲、配色克制，放之四海皆准，跟"你关注的那个博主"毫无关系。
产品卖点明明是「给你关注的人的穿法，落到你衣柜」，可链路里根本没有博主。

ADR 0008 审计确认了五个事实，最致命的两个：
1. **案例库没有一条 URL**——source 全是纯中文文本，不可验证；
2. **inspo 没有任何校验**——「禁止编造博主名」只是写给 LLM 的祈使句，代码里不存在白名单，
   LLM 吐什么字符串就原样高亮到页面。

核心诉求由此确立：**参考的那套韩女搭配必须可溯源，确保不是 AI 自己编的。**

### 2.2 三级分级：找得到一手，就不用二手

案例入库前先验真，分三级：

| 级别 | 定义 | 处理 |
|---|---|---|
| tier 1 | 韩国博主 IG 一手（或对原帖有明确图文解析的国际时尚媒体，文内嵌原帖） | 直接入库 |
| tier 2 | 中文搬运，但可标注 viaOriginal 指回一手 | 须带 viaOriginal 才入库 |
| tier 3 | 国内改写稿（多级转述，细节已失真） | **拒收** |

这是"溯源"的地基：**url 指向的东西本身不可信，后面所有的溯源都是表演。**
易混案例的教训：百度百科的「崔罗娜Rovely」是抖音创作者，不是韩 IG @rloiy——
身份没验清之前宁可不入库（최희진 至今未入库，就是这个纪律的体现）。

另一个纪律：**触碰用户雷区的造型主动排除**（庭沼珉挂脖露背西装、彩领亮粉花裙）。
案例库不是越全越好，是越"对你"越好。

### 2.3 案例的结构化：从「她穿了什么」到「可验证的公式」

一条案例不只是一段描述，而是四层信息，一层比一层"硬"：

```
items          她穿了什么（结构化单品列表）
colorLogic     为什么好看（配色逻辑的自然语言）
transferable   你能抄什么（结合示例用户画像（已脱敏）的迁移分析）
constraints    硬约束公式（mustContain: 外套 oversize ×1 + 内搭 slim ×1 + 下装 regular ×1）
```

**transferable → constraints 是整个供给侧最重要的一次升级**（ADR-0012 决策一）。
之前 transferable 只是 prompt 里的软文本——模型"看了"但没人检查它有没有照做。
升级后，「参考了该案例」有了唯一定义：**生成的 set 真穿出了 mustContain 的结构**。
不满足 → 不得引用该 id（溯源降级）。这是"希望模型参考"变成"模型没法不参考"的供给侧版本。

### 2.4 personal 独立文件：防「换季刷新连坐」

personal-cases.json **绝不并进 brain.json**。
原因：brain.json 是换季整文件覆盖刷新的（meta.description 明说），personal 案例并进去
会被下一次刷新冲掉。独立文件 + brainLoader 加载时合并 + 按 id 去重，刷新互不影响。
且 personal 案例永不参与注入封顶、永远排在 public 前面——个人库是产品差异点的本体，不是补位。

### 2.5 自证字段：构成要能一眼验收

案例池出过一次「聚合值骗局」：日志里 `brain.cases=16` 看起来正常，实际是封顶截断后
personal 一条都没进去的指纹。教训：**聚合数值不可验收**。
修法是 `caseStats()`：把 total/personal/public/fresh/博主名单摊平随响应回传，
前端脚注肉眼可验「博主案例到没到云端」。这成为项目元规则的第一个实例：

> **修完还要能一眼看出修没修好。**（后来演化出 refImageUsed、BUILD_TAG，见 §4.4）

## 3. 消费侧方法论：案例 + 衣橱 + 天气 → 3 套推荐

### 3.1 温度驱动，不跟日历走（ADR 0010）

旧实现用月份推季节，两个系统性错配：9 月仍 30℃ 却注入毛绒开衫思路；更糟的是
12/1/2 月被倒错归入「春夏」——真冬天按夏天推荐，且这种错位**不报错、只是默默荒唐**。

修法是把判定依据从「日历」换成「气温」：当天最高温 → 5 档温度档 → 决定
允许哪些季节标签的单品 + 外套规则 + 是否禁短袖（联合日历季节与最低温，冬季 low<20℃ 禁短袖）。

设计要点：外套**按保暖度判定，不按品类一刀切**——风衣可厚可薄，冬季大温差天
（high 28 / low 12）要「砍厚风衣、留春秋款」，所以炎热档禁的是保暖型外套
（season=秋冬 或带厚/加绒/毛呢标签），薄款照派。

### 3.2 前置过滤：让 LLM 看不见，而不是求它别用

温度档先过滤衣橱候选，LLM 的输入里**根本没有**那件厚风衣。这是「代码校验替代
希望模型自觉」的第一个应用。三层顺序：袖长闸门 → 外套保暖度逻辑 → 基础季节标签。
过滤后为空（衣橱全是过季件）则退回全量，交给 prompt 里的温度规则约束——**宁可放宽到有提示的约束，不可推荐空列表**。

### 3.3 双闸选案例：注入之前就把不合格的拦掉（ADR-0012 决策二）

硬约束升级后出现新矛盾：30℃ 还注入"毛绒开衫"案例，硬约束会逼 AI 凑出荒唐搭配。
所以案例在**进入 prompt 之前**过两道闸：

- **闸 1 季节交集**：案例 season 与温度档 allowSeasons 有交集。
  词表陷阱：案例用「夏秋」、档位用「春夏」——字符串相等永远匹配不上，
  曾导致 9 条案例在所有温度被静默丢弃。修法是**字符级交集**（夏秋 ∩ 春夏 = 夏）。
- **闸 2 可满足性**：案例 mustContain 每一项都能在温度过滤后的衣橱里找到对应单品
  （角色类别 + 版型，经 slotMap 归一化比较）。衣橱没有 oversize 外套，"oversize 外套公式"
  的案例就不注入。

**兜底是诚实降级**：两闸后零案例 → 返回空，退回纯衣橱搭配，不挂案例、不硬凑。
宁可某天没有灵感署名，也不让 AI 硬抄一条满足不了的公式。

### 3.4 prompt 注入：受控 id 必须让模型看得见

promptBuilder 把规则（带 ruleId）和案例（带 id=p-xxx、硬约束文本）渲染进 system prompt，
并立下输出契约：inspoId 只能是本轮注入案例的 id 原样照抄；**只有结构性满足硬约束才能署名**；
参考库外博主或纯通用搭配，inspoId 写空串。
LLM 只有看得见 id 才引用得对——这是白名单校验的前置条件。

三套的固定结构也写死在 prompt 里：第 1 套「今天就能穿」（100% 衣橱、wish 必空），
第 2、3 套「韩女搭配」（≥1 件衣橱锚点 + 可含 wish 种草件）。第 1 套的卖点恰恰是
「你衣柜里就有答案」，拿韩女对照反而暗示还得买东西。

### 3.5 溯源双轨 + 结构优先自动映射（ADR 0008 → 2026-09-03 修订）

LLM 返回后，provenance 做四态判定：

| 态 | 含义 | 处理 |
|---|---|---|
| satisfied | 署名案例 + set 真满足硬约束 | verified，前端展示博主署名 + 三件套 |
| not-satisfied | 署名了但没满足硬约束 | 降级，不得引用该 id |
| not-injected | 署名了没注入过的案例（编造） | 降级 |
| no-ref | 诚实声明没参考 | 合法降级（"通用韩系原则"） |

关键修订（「三套全 FALLBACK」事故）：最初自动映射用**文本重叠度**当闸门，但真实 LLM
的 reason 是自己的措辞、不含案例受控词，重叠度永远不达标 → 明明照公式搭了，全被降级。
修法是把顺序倒过来：**结构满足当主闸（set 真含 mustContain 结构 = 最诚实的映射信号），
文本重叠只给并列候选排序**。LLM 自报命中且约束满足 → satisfied；自报失败 →
结构自动映射；映射无候选 → 诚实降级，绝不硬贴。

另一层务实容错：LLM 常把 p-002 回传成「案例2」「高允贞」「1017kk」这类序号/博主名/子串，
resolveInspo 对这些写法做**确定性还原**（都落在注入集合内，不算编造）；越界序号绝不取。

### 3.6 解析兜底与契约守护

- itemIds 逐一对照安全候选池（温度过滤后的），幻觉出的过季件 id 直接丢弃——
  「前置过滤 + 解析兜底」双保险。
- enforceSet1AllWardrobe：AI 偶尔不听话把第 1 套塞了 wish，代码强行把纯衣橱方案提前/
  清空 wish，守住「今天就能穿」契约。
- wish 每套最多 2 件、每套至少 1 件真实单品（全种草方案直接丢弃）。

### 3.7 懒懒签名：一个设计正确的功能，如何被删干净（ADR 0013 亮调 A → 2026-09-10 全产品下线）

**它原本解决的问题**：上身图下方那句「这套是照 高允贞 「灰色丹宁外套」的穿法来的～示例用户，
选对版型最藏肉」是**确定性字符串组合**（provenance + 用户画像），零新增模型调用。
诚实底线：无 verified 博主时绝不编造博主名，只出画像适配句或「通用韩系思路」。
定位很清楚——**签名是"让已有的溯源可见"，不是"制造溯源"**。

**它为什么被删**：两次都是用户主动否定。
- 2026-09-08 推荐页移除：「懒懒签名没用还占地方」；
- 2026-09-10 收藏页移除：用户在收藏页看到每条卡片都挂着一模一样的
  「通用韩系思路穿搭～示例用户、偏瘦……」，要求统一删掉。

**方法论一：可见性预算有限，信息要排序。** 签名在多数收藏上走的是**通用分支**——
没有 verified 博主时它只会输出"通用韩系思路 + 身形适配句"，即**每条都长一个样**。
一个每张卡都重复、又不携带区分信息的文案，占掉的正是图片、单品名、搭配理由的位置。
在双列卡片这种面积稀缺的场景里（见 §4.6.1 收藏页双列），它必然是第一个被牺牲的。
**"可见的 AI 可被评判" ≠ "每条都要挂满 AI 的话"——可评判的前提是它说的东西有区分度。**

**方法论二：删界面 ≠ 删链路，先分清哪个才是用户诉求。** 用户要的是"界面上不再出现"，
所以本轮只删了前端四处（渲染节点、字段加工、样式、以及一处已失真的注释）。
但云函数 `aiRecommend` **仍在生成** `bloggerNote`、推荐页收藏入库仍在写这个字段、
还有 4 处测试在断言它——全部界面都不再用之后，它变成了**有产出、无消费**的数据。
清理它需要重新部署云函数 + 同步改 4 个测试 + 2 份文档，**成本远大于前端删除**，
且引入一次"必须部署才生效"的风险。取舍：**先删用户看得见的部分，把链路清理记为待决**（§8），
不为了代码整洁去换一次部署事故的可能。

历史收藏文档里已有的 `bloggerNote` 字段**不必迁移**——不渲染即不可见，留在库里无害。

### 3.8 fit 升级：expand–contract 全程（ADR 0014，2026-09-09 闭环）

fit 从「复合中文字符串」升级为「标签数组 + 品类路由词表」，动机来自用户对 Why 的坚持：
**fit 在不同品类的维度本质不同**——内搭是宽紧+长短、长裤是版型+长短、鞋先分鞋型再出
跟高/筒高——「而不是大杂烩」。flat 枚举方案被否，两级字典（品类→维度→标签集）成为唯一真源。

三段推进（expand–contract）：

1. **expand（T01）**：新词表 `fitTaxonomy` 双端同构落地，与新写入并存——旧读侧不动；
2. **migrate（T02 云函数批 + T03 前端批）**：全部消费方兼容 `string | string[]` 双形态；
3. **contract（T03）**：归一化收敛为单路径（先切分再逐段、按写入位置序取主导）。

迁移期最重要的守卫是**等价**：存量数据的行为不能变。一次真实拦截——最初用
「任一标签命中即满足」的宽交集语义，会让存量「修身/常规」对 regular 约束从冲突变满足；
改为「首命中主导」才与旧行为严格等价。教训沉淀：**迁移代码的验收不是「新功能能用」，
而是「旧行为逐 bit 不变」——等价守卫要覆盖语义差异点，不只是抽样。**

收敛时的一个有意差异也被诚实标注：逆序串（「常规/宽松」）的主导版型从别名序变为
位置序——种子与 AI 输出均为「版型在前」的写序，实际无此形态，属于可接受的收敛。

## 4. 出图侧方法论：搭配怎么变成图

### 4.1 按需生成 + 双入口（2026-09-10 旧试穿入口退役后；2026-09-15 spec 0011 手动卡加入）

拼贴（单品图横排）是零成本默认形态；演绎图**只在用户主动点击时生成并计费**，
从不自动生成（ADR 0004）。**出图入口有两个**（spec 0011）：AI 方案卡的「演绎」、
手动搭配卡（用户在选品页自己挑的那一套）的「演绎」——两条入口走**同一条链路**
（同一个 `api.genLook`、同一套缓存键、同一个额度池），手动卡的差别全在内容不在形状，
链路上唯一的分支是一个**独立开关** `coverage`（出图后逐件判「图上可见吗」，AI 卡不传）。

- **演绎**（qwen-image-3.0 多图融合，**单趟**）：AI「画」——人物底图 + 外套/下装平拍图直接进模型
  （图1/图2/图3 硬指代），VLM 先读平拍图生成文字描述（磨白/印花/五金等属性记不下的细节），
  用描述替换属性 token（spec 0003）。无底图时退 wan2.6-t2i 纯文生图兜底。
  配饰（帽/鞋/包）没有参考图槽，只进 prompt 文字——**时常丢失是结构性限制**
  （无图遵循度最低 + 画面位置最差 + 丢失代价最低三者叠加）。结构性正解是两趟生图
  （第二趟以第一趟产出为基底「贴」配饰上去），已立项 `docs/tickets/0009`，未实现；
  **2026-09-15 起有观测手段**（手动卡出图后逐件判可见性并渲染脚注，票 0011-07），
  两趟的优先级由这份数据定。
  人像底图按 refImageType 分流：自拍不进画面（fail-closed），模特图要求身材接近用户
  ——**底图身材决定出图可不可信**。
- **把平拍图真实穿到人像上的专用模型（已退役 2026-09-10，tickets/0008-01/02）**：AI「真穿」，曾以
  像素级保真为唯一卖点。退役原因见 §4.7——早期专用试穿模型列入百炼 2026-10-10
  下线清单且**无对等替代、闭源无逃生通道**。其接口只收 1 top + 1 bottom 两个槽位，
  叠穿内搭、种草件、鞋包配饰天然进不了画面（一套 7 件覆盖率约 2/7），用户实测
  「缺件」是主症状而非保真问题——但保真本身是兑现的（衣服从来是对的）。
  入口已删（推荐页单按钮「演绎」），收藏页历史渲染图仍可显示；保真诉求由票 03
  「衣物保真硬约束进 prompt」承接（待实施）。

### 4.2 缓存键铁律：输入即键

凡影响画面的输入变了，键就必须变，否则旧图被继续命中（「改了但图没变」的根因）。
当前键结构：

```
演绎键 = baseKey(单品集合+场景+PROMPT_VERSION+wish)
         + '-' + renderSalt(参与画面 fileID 串 md5 截12)
         + '-' + provider + '-' + keyTag
         # keyTag = renderModelTag(QWEN_EDIT_MODEL 或 WANX_T2I_MODEL) + '@' + QWEN_EDIT_SIZE
（原旧试穿键 baseKey + AITRYON_MODEL + personSalt 已随早期模型退役删除，0008-02）
```

- PROMPT_VERSION：改 prompt 措辞/构图 → 人工 +1（版本盐）。**尺寸不必**——它已进 `keyTag`（2026-09-17）。
- renderSalt：换模特图/换平拍图 = 新 fileID = 新指纹 = 必然重出（数据侧变化自动换键，无需人工）。
- renderModelTag：换模型 = 键自动变 = 旧图失效重出（无需人工 +1）；prompt 措辞变了仍要 PROMPT_VERSION +1。
- `QWEN_EDIT_SIZE`（输出尺寸）：2026-09-17 从硬编码提成 env 并进 `keyTag`——**「尺寸」与「模型名」分开两列**：
  算键的值可以带 `@尺寸`，给人看的 `modelUsed` 不能（同 0009 的「枚举给门、中文给人」）。
- prompt_extend 显式 false：qwen-image-3.0 默认 true 会自动改写提示词（无报错无日志），必须关死。
- 演绎键拼「参与画面的单品平拍图指纹」——fileID 在 items 文档里，所以读 items 必须
  **前置到算键之前**。meta 同理（人像指纹来自 meta.refImage）。
  这是一条通用顺序纪律：**键逻辑依赖谁，就先读谁再查缓存。**

⚠️ 副作用要有预期：换一次模特图 = 该批搭配缓存全失效重出，调试期极烧生图额度。

### 4.3 meta 单例自愈 + 权限可见性

meta 集合历史原因存在多条文档，读取规则三步收敛：先按 `_openid === OPENID` 收敛到本人
→ 再优先选含新字段（refImage/refImageType）的 → 并列时 _id 大者优先。

`_openid` 收敛这一步是最贵的一课：**云函数是管理员权限，读到库里所有人的 meta；
小程序端受「仅创建者可读写」只读自己的**。两边可见集合不同，就会出现「档案页写 A、
云函数读 B」——症状是换了人像底图仍出旧脸，且档案页照常提示"已更新"，毫无自诊线索。
同类问题的另一版本：库里一条无 _openid 的僵尸文档 _id 最大，静默劫持人像。

页面级纪律：**切参考照类型只改类型字段，绝不联动删除照片资源**（曾因此丢过用户图片）。

### 4.4 部署自证：改完云函数 = 没改，部署了才算

「换了模特图还是旧模特」连修三轮、代码全绿、真机照旧——真因是云函数没重新部署。
这类「代码对、云端旧」的错位在界面上完全静默，用户分不清是没部署 / 缓存没失效 /
读到错文档。修法是把猜测变成可判定事实：

- genLookImage 顶部 `BUILD_TAG`（当前 `2026-09-15.2`），两个出图出口（新生成 + 命中缓存）**都**回传 `build`；
- 出口自证三件套（0008-02，同两出口都回传）：`modelUsed`（实际请求的模型，genCache 同步入库——
  「换 env 生没生效」一眼可判）、`rewriteStatus`（应恒为 not_use，非此值 = 提示词被偷改写）、
  `usageInfo`（输入图张数 + 计费档）；
- 前端顶部 `REQUIRED_CLOUD_BUILD` 比对，不一致弹「云端还是旧版本」。
- ⚠️ 两处各存一份（小程序不能 require cloudfunctions），改一边必须同步另一边。

### 4.5 月额度按北京时间

`toISOString().slice(0,7)` 是 UTC 月，慢 8 小时——每月 1 号 00:00–08:00 的生成被记到
上个月，且档案页显示与云函数判定打架。修法：`getTime()+8h` 后用 `getUTC*` 读，
不随容器时区漂移。前端 profile 页有一份同构实现，**改一处必须同步另一处**。

### 4.6 呈现与出口：结果怎么落到用户手上（2026-09-10）

图生成出来了，还有两件事决定体验：**卡片怎么排**、**图怎么存到手机**。这两件同一天被返工过，
而且都栽在同一个认知上——**"看起来能用"不等于"契约正确"**。

#### 4.6.1 收藏页双列：顺序契约不是 CSS 能表达的

用户三句话逐步逼出真正的约束：
①「一条占高太大，改双列」→ ②「不用硬性对齐，下面一条紧靠上面一条」→
③「左侧那列是最近的，右侧那列是上周的」。翻译成工程语言是三个同时要满足的条件：
**列内紧贴 + 时间倒序 + 最新一条在左上角**。

CSS 方案逐个试过，没有一个同时满足：

| 方案 | 列内紧贴 | 最新在前 |
|---|---|---|
| `grid` + `align-items:start` | ❌ 按行对齐，同行矮卡片下方必然空一片 | ✅ 行优先填充 |
| `column-count: 2` | ✅ | ❌ **列优先填充**：填满左列才排右列 → 右列全是旧数据 |
| **JS 交替分列 + 两列 flex** | ✅ | ✅ 第 1 条永远在左上角 |

教训：**CSS 的"自动布局"只在它的排序语义与业务语义一致时才可用**。grid 的行优先、
多列的列优先，都是合理但不是你要的语义；一旦冲突，唯一出路是**把顺序交给代码**，
而不是继续用 CSS 技巧硬凑。

分列逻辑因此抽成纯函数 `splitColumns`，并把顺序契约钉进断言
（`pages/looks/sourceFilter.test.js` T7：左列必须是第 1/3/5 条、**`L[0]` 必须是最新那条**）。
价值在于：将来谁"顺手"把分列换回 CSS，测试直接红——**不靠人肉发现，靠门拦**。

同一轮的另一条小纪律：衣橱页从"两列自适应"改成固定三列时，用的是固定列数而非调小
`minmax` 阈值。因为 `auto-fill + 像素阈值` 等于**把列数交给屏宽决定**，而用户要的是
固定的视觉密度——窄屏（320px）也得保持一排三件，靠卡片内部字号自适应。

#### 4.6.2 保存到相册：失败必须能分类，不能合并成一句话

用户报「推荐页和收藏页保存到相册总失败」。静态排查后**代码本身是对的**：调用顺序对
（先 `downloadFile` 拿临时路径，再喂相册）、参数绑定对、fileID 是合法云文件 ID。
症状因此指向微信侧的两道关（权限 / 隐私合规）。

真正的障碍不是 bug 本身，而是**可观测性**——原实现是：

```js
.catch(() => { wx.hideLoading(); wx.showToast({ title: '保存失败', icon: 'none' }); });
```

`.catch` 把 wx 返回的错误码整个丢掉了。「下载失败」「用户没授权」「小程序后台没配隐私声明」
三种完全不同的故障，在界面上长得一模一样。**用户能做的只有反复点，反复失败，然后来问。**

于是这一轮**没有猜着改**，按诊断纪律做了三件事：

1. **没有反馈环时先插桩，不要先假设。** 这类 bug 无法在本地复现（要真机相册 + 微信隐私校验），
   所以第一步是把被吞掉的 errMsg 原样暴露出来——失败自己会说话。这一步的产出本身就是进展：
   下次点保存，弹窗会直接告诉你卡在哪一环。
2. **抽一个可测的接缝。** 「下载 → 存相册」抽成注入式模块 `utils/saveImage.js`（wx 作为入参传入），
   Node 里可直接单测：9 条断言覆盖空 fileID / 下载失败 / 下载没给临时路径 / 授权被拒 /
   隐私未声明 / 未知失败 / 成功，其中一条专门钉死**「相册接口必须吃 tempFilePath，不能吃
   `cloud://` fileID」**这个最经典错法。
3. **失败分类必须对应"用户下一步能做什么"。** `privacy`（后台未声明相册权限 → 去小程序后台配置）
   与 `needSetting`（用户自己拒过授权 → 去设置页打开）**必须是两类**，因为解法完全不同。
   合并成"保存失败"，等于把定位工作全丢回给用户。

配套纪律（写进 CHEATSHEET §0.6）：两页共用同一个模块，**禁止各写一份**（原来就是各写一份、
各吞各的错）；保存失败一律 `showModal` 而非 `showToast`——后者约 14 字截断，原始错误根本显示不下。

> 这已经是同一个元问题的第四次现身：案例全失踪、换模特图、部署错位，
> 到今天的保存失败。每次根因都是同一句话——**修完还要能一眼看出修没修好**。
> 插桩不是"临时日志"，它是把"下次失败可判定"变成永久能力。

### 4.7 模型生命周期：这次为什么迁、迁了买到什么（tickets/0008，2026-09-10）

**导火索**：百炼公告（2026-07-10 发布，10-10 生效）下线整个 qwen-image 老家族
（11 个模型，含演绎的 `qwen-image-edit-plus-2025-10-30` 与早期专用试穿模型），
官方替换一律 `qwen-image-3.0`。不迁 = 演绎当天断供；早期专用试穿模型因无对等替代直接退役。

四条沉淀：

1. **快照 vs 主线 = 30 天 vs 3 个月预警。** 当初钉快照版防「latest 漂移」没有错，
   但换来的是预警窗口从 3 个月缩到 30 天。迁主线（无日期后缀）是结构性降险——
   防漂移与预警时长不可兼得，但预警时长是可以选的。
2. **开源权重 = 逃生通道。** 早期专用试穿模型是百炼独家闭源，下线即死透；qwen-image 开源，
   阿里不托管了还能换别家（硅基流动同款权重）乃至自部署。**选模型先问一句：
   它死了我还能从哪拿到它？**
3. **付费方式不改变可用性。** 资源包/节省计划按模型名严格匹配、跨版本不通用，
   「充年卡规避下线」是伪命题——包是更便宜的钱，不是更长的命。
4. **让下次换代退化成改 env。** 模型名全部环境变量化（QWEN_EDIT_MODEL / WANX_T2I_MODEL /
   SF_I2I_MODEL / SF_T2I_MODEL），缓存键拼模型名（换代自动重出），出口回传 modelUsed
   （env 生没生效一眼可判）。配套「已退役渠道显式拒绝」：传死模型名报错而非静默换渠道——
   静默换渠道会让「为什么图变了」无从归因。

**效果对比的纪律**：迁移与 prompt 语义变更（票 03 保真约束）**刻意分两次做**——
模型和提示词同时改，效果变好变坏分不清是谁的功劳。A/B 对比窗口只到 10-10
（此后旧模型永逝），方法：控制台加 env `QWEN_EDIT_MODEL=旧模型名` 出一版 → 删 env 再出一版，
同套搭配同模特图，genCache 两版并存（键含模型名）互不覆盖；对比完**必须删掉该 env**。

## 5. 入口侧方法论：衣服怎么进衣橱（spec 0006，2026-09-09）

### 5.1 页面只做 IO，状态机全部纯函数

上传链路有七种单张状态、三种失败退路、一条串行推进规则——这种复杂度放进页面代码
必然失控。做法是全部状态转换收敛进纯函数模块（queue.js / panel.js / itemDoc.js），
页面只做三类 IO：选图、上传、调云函数。收益直接可见：**30 个离线测试守卫
全部 node 直跑**，改一行状态机 3 秒出红绿，不用起开发者工具。

抠图是唯一「不在纯函数里」的一环——它需要真模型（见 5.4），只能进云函数；
但页面侧仍只做「发起 + 轮询 + 拿 fileID」，状态机（queue.js）完全不知道抠图换了实现。

配套纪律：页面间不复制逻辑——fit 编辑三件套从上传页面板下沉到 utils/fitTaxonomy，
编辑页（item-edit）与上传页共用同一实现。跨页面 require 页面文件会执行 `Page()` 注册，
共享逻辑只能进 utils（同 PALETTE 提取的教训）。

### 5.2 AI 永不自动写库

「确认入库」是用户必点的一步——AI 识别结果只进预览，没有任何自动落库路径
（状态机上 previewing 不可前进，测试显式守卫）。这是「诚实降级」哲学在入口侧的
翻版：AI 可以预填，但「这件衣服进你的衣橱」这个决定必须是人的。

### 5.3 失败路径必须有退路

最初上传失败只有「重新上传」——用户网络不好会被锁死在队列里，且「全部失败」的
收尾场景永远无法到达。修法是给每种失败都配退路：上传失败可跳过（不入库）、
抠图失败可用原图继续（不阻塞）、识别失败可手动填写（AI 挂了流程不断）。跳过不计入
成功数，汇总如实显示「已添加 X 件，跳过 Y 张」。

同一哲学的另一面：抠图失败不阻塞——红字提示 + 回退原图继续，因为「这张没抠好」的
代价远小于「整个批次卡住」。

### 5.4 抠图为什么从色键换成真模型（ADR-0016）

抠图一开始是**纯算法**的：边缘带中位数采样背景色 + Chebyshev 距离硬阈值（30/255），
零成本、毫秒级、离线可测。ADR-0015 还想给它加一层「色键失败 → 生成模型重绘绿幕 →
再色键」的兜底。真机跑下来两个结论推翻了这套：

1. **色键的天花板是算法层的，调参救不了**。单参考色在渐变/阴影/杂物背景上代表性崩塌；
   二值硬阈值导致锯齿、以及把参考色附近的衣物像素一并抠掉（衣服上打洞）。
   更麻烦的是「抠错了但 coverage 落在正常区间」——系统自认为成功，用户拿到烂图。
2. **让生成模型重绘背景是错误的方向**。`wanx2.1-imageedit` 没有 alpha 通道，只能把背景
   「画」成绿色再抠。而生成模型会顺手改动衣物本身（颜色偏移、纹理丢失、纽扣变形）。
   衣橱是推荐系统的真源——一件「正红」被重绘成「偏橘红」，后面所有颜色逻辑都建立在假数据上，
   而且**全程静默**（用户只觉得「怎么推荐得不对」）。

教训：**「省钱的第一级 + 兜底」这种分层看似稳妥，但如果第一级的「成功」本身就不可信，
留它等于留住用户抱怨的那个质量**。用户最终拍板「全量走腾讯云数据万象 GoodsMatting」——
真抠图（输出带 alpha 的透明 PNG），不做分层，不赌模型不会改衣服。代价是每张都计费
（0.01 元/次 = 通用抠图 0.02 元/次 × 抵扣 2:1，2023-12-01 调价后实际价；免费 1000 次/2 月），换来的是「入库的图就是这件衣服本身」。

工程上仍守住了两条老纪律：① detect-url 模式让图片不必迁出微信云存储（云存储仍是唯一真源）；
② 同步接口照样套 start/poll 外壳 + 代次令牌（客户端 3s 硬超时是平台约束，与抠图换不换实现无关）。

#### 选型时踩过的坑与复核（ADR-0016，2026-09-10）

**坑一：把"调价前的旧价"当成现价，去"更正"一份本来写对的 ADR。**
0.14 元/次是数据万象的**旧计费标准**；2023-12-01 起改为「通用抠图 0.02 元/次 × 抵扣比例 2:1」，
即实际 **0.01 元/次**（免费额度 1000 次 / 2 个月）。我一度拿 0.14 去纠正 ADR-0015 里正确的那笔账，
**改错了方向**。
> 教训：改价公告里「原计费标准 / 调整后计费标准」是**成对出现**的，必须整页读完，
> **永远取「调整后」那一栏**。只抓到第一个数字就动手，等于把旧价当新知。

**坑二（更重要）：比单价之前，先比"最后一公里"的约束。**
写完 ADR 后又做了一次三方复核，结论差点翻盘：

| | 腾讯 GoodsMatting（已落地） | 阿里 商品分割 / 服饰分割 |
|---|---|---|
| 是否真抠图（带 alpha） | ✅ | ✅ |
| 单价 | 0.01 元/次 | **0.002 元/次**（便宜 5 倍）|
| 免费额度 | 1000 次 / 2 月 | 13,333 次 / 1 年 |
| **输入上限** | ≤32MB / ≤50000px | **≤3MB / <2000~3000px** |
| 输出形态 | 响应体直出二进制 | 30 分钟过期的临时 URL |

**决定性差异是输入上限，不是单价。** 手机原图普遍 3000×4000、3–5MB，走阿里**必须先压缩**
（多一轮真机调参 + 边缘细节损失），走腾讯原图直传。
> 教训：单价便宜 5 倍听着像铁一样的事实，但它落在"最后一公里"的约束上就未必成立——
> 便宜的钱可能被一道新增工序（压缩、调参、质量损耗）吃回去。**选型要把账算到"用户拿到的那张图"为止。**

顺带一个成本结论（顺手把担心的账算清）：**detect-url 模式图片不进 COS**，
所以 COS 桶可以永远空置——存储费、请求费、流量费全为 0，**不需要任何定时清理任务**。
唯一支出就是调用费。这也印证了那条架构手法：**外部图像服务可以直接消费微信云存储的 fileID，
云存储始终是唯一真源**（ADR-0001 未被动摇）。

#### 部署状态（2026-09-10，卡在用户侧开通）

代码与离线守卫（签名快照 / 错误七分类）已完成，`mattingAI` 旧云函数与客户端色键已退役。
真机启用还差用户侧五步：腾讯云实名 → 建 COS 桶并绑定数据万象 → 开通「AI 内容识别」
→ 配 4 个环境变量 `COS_SECRET_ID/KEY/BUCKET/REGION` → **云开发控制台手动删除已部署的旧 `mattingAI`**。
⚠️ **删本地源码 ≠ 删云端实例**——这一步只能人工做。部署后真机验收 = 传一张复杂背景衣物照，
看透明 PNG 是否干净、且衣物本身与原图一致（不被重绘改动）。详见 CONTEXT ④ 第 8 条。

## 6. 贯穿全链路的八条心法

1. **输入即键**：凡影响画面的输入（代码版本、模型、人像、平拍图、wish）变了，缓存键必须变。
2. **诚实降级优于硬凑**：零案例退纯衣橱、编造署名降级、无 verified 博主不出签名、
   自拍禁进画面（fail-closed）。「宁可少一个功能，不可多一个谎言。」
3. **代码校验替代希望模型自觉**：前置过滤、双闸、白名单、硬约束校验、确认入库必点，全是同一哲学的实例。
4. **自证**：凡「云端读了哪个值决定结果」的链路，把实际取用的值回传前端（caseStats /
   refImageUsed / build / modelUsed），让"修没修好"变成肉眼事实，而不是靠结果反推。
   **失败也要自证**：错误必须分类到"用户下一步能做什么"（如保存相册的 privacy / needSetting
   两类），并用 showModal + 原始 errMsg 呈现。合并成一句"失败了"，等于把定位工作全丢给用户。
5. **词表归一化**：真实数据不是受控枚举——fit 是「宽松/长款」复合中文，季节有两套词表
   （单品「春秋」/ 案例「夏秋」）。比较前必归一，归不了类的按"无法证伪"放行，
   别让脏数据静默消失。合成夹具永远测不出这类断裂，守卫测试必须用真实数据跑。
6. **部署了才算改了**：云函数改完必须上传部署；且前端要能自证云端版本（BUILD_TAG 机制）；
   版本盐清单按 grep 全仓跑，别背（2026-09-09 有第三处硬编码漏改的教训）。
7. **失败路径必须有退路**：锁死比失败更糟——每种失败都配「重试」+「放弃/降级继续」两条路，
   且放弃要计入汇总（诚实），不能静默消失。
8. **纯函数优先，IO 越薄越好**：状态机/算法/形状转换全部抽纯函数，页面只做 IO——
   离线可测是 TDD 全绿的基础，也是复杂链路敢改的前提。
   连"顺序"也是一种契约：收藏页双列的分列抽成 `splitColumns` 并配断言（最新一条必须在左上角），
   免得它被"顺手"改回 CSS 实现却无人察觉。**能被断言钉住的约定，就不要靠人肉记住。**

## 7. 事故与未遂复盘（方法论是怎么被"烧"和被"拦"出来的）

**事故一：「案例全失踪」（2026-09-03）**
症状：案例注入了，三套推荐却全部显示「通用韩系原则，无特定参考」。
排查：修复方向对了两轮都没好，根因在**无法验收**——日志只有案例总数这种聚合值。
根因：自动映射拿文本重叠度当闸门，真实 LLM 措辞不含受控词 → 永远不达标。
沉淀：结构满足当主闸（§3.5）+ caseStats 自证字段（§2.5）+「聚合数值不可验收」纪律。

**事故二：「换了模特图还是旧模特」（2026-09-05，拖三轮才定位）**
症状：换人像底图后仍出旧脸，档案页却提示更新成功。
三轮根因依次：① 缓存键缺人像指纹 → 加 personSalt；② 页面 genImage 已存在时静默 no-op →
onShow 比对指纹清空 genImage（一次 setData 内完成）；③ 云函数读到了别人的 meta 文档
→ `_openid` 收敛。最后发现**代码全绿真机照旧**——第四层根因是云函数根本没重新部署。
沉淀：输入即键（§4.2）+ meta 收敛（§4.3）+ BUILD_TAG 部署自证（§4.4）。
元教训：这类错位界面完全静默，必须靠自证字段把三种可能（没部署/没换键/读错文档）变成可判定。

**事故三：「额度显示打架」（2026-09-04）**
症状：档案页显示「已用 0/60」，云函数却判「额度用完」。
根因：UTC 月 vs 北京时间的 8 小时差，月初凌晨的生成记错月。
沉淀：localMonth 固定 +8h 用 getUTC* 读（§4.5）；**测试夹具的 usage.month 也要用同一实现**，
否则月末月初跑测试假红。

**未遂事故四：上传链路的 P0 三连（2026-09-09，离线评审全部拦下）**
与前三起相反，这一组**没有烧到真机**——三个 P0 全部被离线 code-review 在实现阶段拦截：
① 识别返回空 → 预览区无按钮，单张永久锁死；② 重试/跳过后旧轮询循环复活，双循环并发 +
假弹窗；③ 迁移宽交集语义违反「行为等价」（存量「修身/常规」对 regular 约束由冲突变满足）。
沉淀：§5.3 失败退路 + 代次令牌 + 迁移等价守卫（§3.8）。
元教训：**事故不一定要在真机上烧过才能沉淀方法论——离线双轴评审（Standards/Spec 分开审）
+ 语义级守卫测试，能把「烧钱才能学到」的课提前变成守卫。** 前提是评审要真读规格原句、
真跑 grep 全仓，而不是走形式。

**进行中事故五：保存到相册总失败（2026-09-10，根因待定案）**
症状：推荐页、收藏页点「保存到相册」总失败，界面上只有「保存失败」四个字。
排查：调用顺序、参数绑定、fileID 合法性**全部正确** → 症状指向微信侧的权限或隐私合规，
而不是本项目代码。
真正的障碍在**可观测性**：`.catch` 吞掉了错误码，于是「下载失败 / 用户没授权 /
后台没配隐私声明」这三种完全不同的故障长得一模一样——用户只能反复点、反复失败。
已做（详见 §4.6.2）：把被吞的 errMsg 分类暴露（`privacy` / `needSetting` 两类）、
抽成可单测的 `utils/saveImage.js`（9 条断言）、两页共用同一份（原先各写一份）。
待定案：本地无法复现（需要真机相册 + 微信隐私校验），已请用户跑一次带回**原始错误文本**。
假设排序：① 小程序后台未声明「相册（仅写入）」隐私权限（最可能——旁证是上传照片正常，
说明配过读取侧，但写入是**独立一项**，极易漏，且漏了就是 100% 失败）② 用户曾拒绝过授权
③ 只在开发者工具里测 ④ 下载失败。
> 方法论先记一条：**拿不到反馈环时，不要先猜着改——先把失败暴露出来。**
> 插桩本身就是进展；在可观测性补齐之前，任何"修复"都无法被验证。
