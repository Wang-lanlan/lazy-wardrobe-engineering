## L1 · 复刻验证体系

目标：证明「公开仓的工程纪律是可运行的」这一主张可复现。

### 前置

- 装好 git + **Node ≥ 22**（演示门零依赖，无需 `npm install`）
- 一条命令查版本：`node -v` → 应打印 `v22.x`

### 步骤

```bash
# 1. clone（公开仓，约 40 个跟踪文件）
git clone https://github.com/Wang-lanlan/lazy-wardrobe-engineering.git
cd lazy-wardrobe-engineering

# 2. 跑自包含演示门
node dev/demo-gates/run.js
```

**期望输出（退出码 0）**：

```
  PASS  budgetGatePreEstimation.test.js
  PASS  cacheKeyVersionSalt.test.js
  PASS  fitRoundTrip.test.js

演示门：3/3 PASS
```

退出码非 0 = 有门转红。CI 里直接 `node dev/demo-gates/run.js` 即可当门禁。

### 进阶：证明你验的是线上那份

clone 后最好确认本地 HEAD 与 GitHub 远端一致，免得评的是旧快照：

```bash
git rev-parse HEAD                       # 本地
git ls-remote origin HEAD                # 远端（需联网）
```

两个 sha 逐字相同 = 你验的就是线上当前那份。（本机若从未 `git fetch`，`origin/main` 引用可能不存在，用 `ls-remote` 比对即可。）

### 关键：反向验证（证明「门能红」，而不只是「门常绿」）

门绿不代表门有效。**绿得可疑时，先证明它能红**。演示门自带「守什么」的声明，照它短路：

```bash
# 1. 编辑演示门①，把版本盐短路成常量（模拟「版本变了键不变」的旧 bug）
#    文件 dev/demo-gates/cacheKeyVersionSalt.test.js 第 16 行：
#       'v' + String(opt.version),
#    改成：
#       'v' + '1',
#    （这样 version=1 和 version=2 算出的键完全相同）

# 2. 重跑 → 期望 FAIL（退出码 1）
node dev/demo-gates/run.js
#   演示门：2/3 PASS   ← 门① 转红，证明它在守「版本盐变了键必变」

# 3. 还原，千万别 commit 这次改动
git checkout -- dev/demo-gates/cacheKeyVersionSalt.test.js
node dev/demo-gates/run.js               # 回到 3/3 PASS
```

三步成立 = 这道门**真的在守东西**，不是永远绿的装饰品。

### L1 能证明 / 不能证明

- ✅ 证明：公开仓的「纪律可运行、且可被否证」主张**可复现**。
- ❌ 不能证明：业务代码正确、推荐质量好、方法论对别的场景有效——那些是 L2/L3 的事。

## L2 · 复刻工程方法论

目标：把这套「可证伪的工程纪律」搬到**你自己的项目**，而不是重跑他们的门。

### 核心认知

你搬的是**方法**，不是他们的测试门。公开仓的 40+ 业务门依赖私有大脑（`cloudfunctions/`、`pages/`、`utils/`、案例库、个人画像），这些**不公开**。你能搬的是**骨架、纪律、文档范式**。

### 可搬运清单（公开仓真实存在的文件）

| 类别 | 路径 | 你拿到的东西 |
|---|---|---|
| 门骨架 | `dev/demo-gates/run.js` + `*.test.js`（5 文件） | 零框架、零业务依赖的门运行器与三道范例门 |
| 门写法 | `dev/demo-gates/README.md`「一道门该有的形状」 | 门的 4 点规范 |
| 决策记录 | `docs/adr/`（19 条 ADR） | 怎么写「带反证」的决策记录（重点看 ADR-0016 主动找反证） |
| 总方法 | `docs/METHODOLOGY.md` | 两趟渲染、缓存键、预算闸等架构纪律 |
| 验证判据 | `docs/VERIFY-CRITERIA.md` | 7 阶段「通过/可疑/否决」判据表 |
| 项目入口范式 | `CONTEXT.md` | ③.4 测试门登记区、铁律区、「不写聚合数字」纪律 |

> ⚠️ **纠正一个常见误解**：`schema-check.js`（大脑 schema 校验）与 `personal-cases.template.json`（案例库模板）**不在公开仓**（是私有资产，未被 git 跟踪）。所以你**拿不到具体的大脑 schema**，只能拿到「怎么造 schema / 怎么写门守它」的范式。L2 给你的就是范式，不是成品。

### 一门该有的形状（摘自 `dev/demo-gates/README.md`）

1. 文件名 `*.test.js`，`node` 直跑，**不引任何框架**；
2. 用 Node 内置 `assert`，**断言失败就抛异常 → 进程退出码非 0**；
3. 门只验证「被守护的条件」——失效时静默给错结果、不报错，所以**必须用反向验证证明它在守**；
4. 顶部注释写清「为什么要有这道门」+「对应哪条铁律 / 哪次事故」。

### 纪律规则（摘自 `CONTEXT.md` ③.4）

- 测试门登记**只列条目与路径**，**不写总数与「N/N」这类聚合数字**——断言数会随维护漂移，文档里的数字迟早对不上（2026-09-10 老教训）。想知道条数就跑一遍。
- 铁律是**活文档**：每次改代码若动了某条铁律的适用边界，回 `CONTEXT.md` 更新，别在别处复述。

### 你的复刻步骤（照做）

1. **搬骨架**：把 `dev/demo-gates/` 整个目录复制到你项目，作为门运行器起点。
2. **写你自己的门**：针对你项目的「静默失效」风险（缓存键、词表归一、预算闸、状态机……），按上面 4 点逐一写 `*.test.js`。每道门先想清楚「短路它必转红」的验证方式。
3. **立 CONTEXT.md**：仿本文档结构，写「铁律区 + ③.4 测试门登记区」。铁律清单见 `docs/VERIFY-CRITERIA.md` §6（输入即键 / 诚实降级 / 自证 / 词表归一化 / 失败路径有退路 / 纯函数优先 等），按你项目取舍。
4. **写 ADR**：每个有争议的决策写一篇，强制写「**反证 / 失效条件**」一节——说不出在什么条件下会变错，那不是决策，是信念。
5. **挂 CI**：`node dev/demo-gates/run.js`（或你自己的运行器）作为门禁，退出码非 0 即阻断。

### 验证你自己的方法论（指向 VERIFY-CRITERIA.md）

搬完别只看过得去，用 `docs/VERIFY-CRITERIA.md` 的 7 阶段判据逐档自审：

- **阶段 2（门可红）** 是最容易被跳过的——你搬的每道门，都做一次「短路→必转红→还原复绿」。
- **阶段 5（后验指标）** 才是方法论真的有用的信号：某类事故在你新门上线后，**复发序数停止增长**。门上线后同类事故仍复发且序数 +1，就是全流程信息量最大的「门选错条件」信号。
- **阶段 6（边界自查）** 要求：用公开层数据撑起的结论，不能偷偷引用私有层数字。

## 一句话总结

- **L1 = 跑通演示门（3/3）+ 反向验证（短路必转红）**——证明公开仓的纪律是真的。
- **L2 = 搬骨架/ADR/CONTEXT 范式 + 照 4 点写你自己的门 + 用 7 阶段判据自审**——把纪律变成你项目的肌肉记忆。

两者都不需要任何私有资产；L2 给你的是「怎么造门守东西」的方法，不是现成的大脑。
